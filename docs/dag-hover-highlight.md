# Commit Trail — Git DAG Hover 하이라이트 개발 명세

## 1. 작업 목적

Commit Trail의 Git DAG에서 마우스 Hover를 이용해 특정 브랜치의 경로와 커밋 메시지에 집중할 수 있도록 개선합니다.

복잡한 분기·병합 그래프에서 관심 없는 경로를 흐리게 표시하여, 사용자가 원하는 브랜치의 변화와 작업 내용을 쉽게 파악하는 것이 목적입니다.

### 기본 원칙

- 기존 Canvas 2D 렌더러 재사용
- Hover가 가능한 데스크톱·넓은 화면 중심
- 브랜치 경로·커밋 노드·메시지를 함께 강조
- 다른 경로의 불투명도 50%
- Git DAG의 실제 부모 관계 존중
- 기존 레인·색상·정렬·스크롤 정책 유지
- 새로운 GitHub API 요청 및 UI 설정 추가 금지
- 일반 화면과 Split view에 동일한 동작 적용

## 2. Hover 대상

### 2.1 브랜치 이름 배지

브랜치 이름 배지에 마우스를 올리면 해당 브랜치를 강조합니다.

- 브랜치 HEAD에서 시작하는 기존 시각적 경로를 대상으로 합니다.
- 해당 경로의 연결선과 커밋 노드, 메시지를 강조합니다.
- 다른 경로는 불투명도를 50%로 낮춥니다.
- 기존 브랜치 전체 이름 툴팁은 유지합니다.
- 동일 커밋에 여러 브랜치 이름이 있는 경우, Hover한 배지에 해당하는 브랜치만 대상으로 합니다.

### 2.2 커밋 노드

커밋 노드에 마우스를 올리면 해당 커밋의 시각적 경로를 강조합니다.

- 커밋이 속한 경로를 명확하게 판단할 수 있으면 그 경로를 강조합니다.
- 커밋이 여러 브랜치에 공유되어 특정 경로를 확정하기 어렵다면 임의로 하나를 선택하지 않습니다.
- 경로를 확정할 수 없는 경우 해당 커밋만 강조하거나 전체 하이라이트를 적용하지 않습니다.

커밋의 SHA나 레인 색상만으로 브랜치 이름을 임의 추정하지 않습니다.

### 2.3 커밋 메시지

커밋 메시지 Hover는 해당 커밋 노드 Hover와 동일하게 처리합니다.

- 메시지와 노드가 같은 하이라이트 대상을 사용합니다.
- 커밋 메시지가 화면 너비에 따라 숨겨진 경우 별도의 Hover 영역을 만들지 않습니다.
- 기존 클릭·탭으로 커밋 상세를 여는 동작을 유지합니다.

### 2.4 빈 공간

그래프의 빈 공간으로 마우스를 이동하거나 그래프 밖으로 나가면 하이라이트를 해제합니다.

모든 요소는 즉시 기존 불투명도로 복원합니다.

## 3. 하이라이트 표시 정책

| 그래프 요소 | 강조 대상 | 비대상 |
|---|---|---|
| 커밋 노드 | 100% | 50% |
| 브랜치 연결선 | 기존 불투명도 유지 | 기존 값의 50% |
| 브랜치 이름 배지 | 기존 표시 유지 | 기존 값의 50% |
| 커밋 메시지 | 100% | 50% |
| SHA·작성자 | 기존 표시 유지 | 기존 값의 50% |
| Actions 도넛 | 기존 정책 유지 | 기존 정책 유지 |
| 태그·릴리즈 아이콘 | 기존 정책 유지 | 기존 정책 유지 |

### 세부 정책

- 기존 브랜치 색상은 변경하지 않습니다.
- 강조 대상의 선 굵기·노드 크기를 불필요하게 확대하지 않습니다.
- 비대상 요소의 불투명도만 낮춥니다.
- 연결선처럼 기존 불투명도가 적용된 요소는 상대적으로 50% 감소시킵니다.
- Actions 도넛과 태그·릴리즈 아이콘은 성공·실패·진행 중 등의 의미를 유지하기 위해 흐리게 처리하지 않습니다.
- 기존 커밋 선택 강조와 Hover 하이라이트는 별도로 유지합니다.

새로운 색상이나 배경 강조 효과는 추가하지 않습니다.

## 4. 브랜치 경로 판정

### 4.1 기존 데이터 활용

현재 구현된 다음 정보를 우선 활용합니다.

- 커밋의 실제 부모 SHA
- `branchTracks()`의 브랜치별 시각적 경로
- `graphColors()`의 노드·간선 색상 정보
- `Graph.tsx`의 커밋 좌표·레인 배치
- 브랜치 이름 배지의 실제 참조 정보

브랜치 색상만 비교하여 동일 경로라고 판단하지 않습니다.

### 4.2 강조 범위

브랜치 배지 Hover는 현재 화면에 표시되는 해당 브랜치의 시각적 경로를 기준으로 합니다.

- 해당 브랜치 HEAD부터 기존 경로 추적 정책을 따릅니다.
- first-parent 경로를 기본으로 합니다.
- 기존 경로가 다른 브랜치에 합류하는 지점에서 종료됩니다.
- 합류 이후의 공통 이력을 무조건 모두 강조하지 않습니다.
- 미조회 커밋을 추가로 가져오지 않습니다.
- 새 데이터가 로딩되면 기존 정보를 바탕으로 경로를 다시 계산합니다.

실제 Git 조상 관계와 화면에 표현된 경로의 차이를 고려하여, 사용자가 보는 그래프와 하이라이트가 일치하도록 합니다.

### 4.3 공유 커밋

하나의 커밋이 여러 브랜치에 포함되는 상황을 고려합니다.

- 같은 HEAD를 공유하는 브랜치는 기존 배지 표시를 유지합니다.
- 브랜치 배지 Hover에서는 해당 브랜치의 경로를 우선합니다.
- 커밋 Hover에서 여러 경로가 겹치면 근거 없이 하나를 선택하지 않습니다.
- 공유 커밋이라는 이유만으로 관련된 모든 브랜치를 한꺼번에 강조하지 않습니다.

같은 기준 줄기 위의 서로 다른 HEAD도 공유 커밋 정책을 적용합니다. 예를 들어 선형 이력 `d4 → d3 → d2 → d1`에서 기준 브랜치 `dev`가 `d4`, `main`이 `d2`를 가리킨다면 다음과 같이 동작합니다.

- `d4`·`d3` 노드나 메시지는 유일한 `dev` 경로(`d4`~`d1`)를 강조합니다.
- `d2`·`d1` 노드나 메시지는 두 경로가 공유하므로 해당 커밋만 강조합니다. 기준 브랜치라는 이유로 `dev`를 우선하지 않습니다.
- `dev` 배지는 `d4`~`d1`, `main` 배지는 `d2`~`d1`을 강조합니다. 원하는 브랜치를 명시하려면 해당 배지를 Hover합니다.

### 4.4 병합 커밋

병합 커밋은 부모가 여러 개일 수 있습니다.

- 기존 first-parent 기준 경로 정책을 존중합니다.
- 다른 부모를 통해 들어오는 병합 연결선은 실제 관계를 유지합니다.
- 하이라이트를 위해 Git DAG 간선이나 레인 배치를 변경하지 않습니다.
- 병합 관계가 불명확한 경우 정확성을 우선하고 무리한 강조를 하지 않습니다.

## 5. 기존 UI와의 연동

### 커밋 상세

- Hover만으로 상세 팝업을 열지 않습니다.
- 기존 클릭·탭으로 상세를 엽니다.
- 상세가 열려 있어도 Hover 하이라이트는 독립적으로 동작합니다.
- 커밋 선택 강조는 기존 정책을 유지합니다.
- Hover가 해제되면 기존 커밋 선택 상태는 그대로 남습니다.

### 브랜치 툴팁

- 브랜치 배지의 기존 전체 이름 툴팁을 유지합니다.
- Hover 하이라이트 때문에 툴팁이 깜빡이거나 위치가 이동해서는 안 됩니다.
- 기존 배지 충돌 회피·말줄임·세로 나열 정책을 유지합니다.

### Split view

- 각 저장소 열에서 Hover를 독립적으로 처리합니다.
- 한 저장소의 Hover가 다른 저장소를 흐리게 만들지 않습니다.
- 기존 독립 스크롤·공통 자동 갱신·저장소 헤더 드래그 동작을 유지합니다.
- 좁은 열에서도 기존 그래프 표시 정책을 유지합니다.

## 6. 반응형 및 모바일 정책

이번 기능은 Hover가 가능한 포인터 환경에서만 적용합니다.

- 마우스와 Hover를 지원하는 포인터 대상
- 모바일 터치에서는 기존 동작 유지
- 롱 프레스 하이라이트 기능 추가 금지
- 모바일 커밋 선택·상세·스크롤 유지
- 화면 크기가 변경되어도 경로 판정 오류가 발생하지 않도록 처리

화면 너비만으로 기능 사용 여부를 판단하지 않고 포인터의 Hover 지원 여부를 고려합니다.

Split view에서는 열이 좁더라도 데스크톱 마우스 Hover를 사용할 수 있어야 합니다.

## 7. 성능

Hover 동작은 빈번하게 발생하므로 불필요한 연산을 최소화합니다.

- Hover 경로 판정은 기존 로딩 데이터만 사용합니다.
- Git DAG 레이아웃을 마우스 이동마다 다시 계산하지 않습니다.
- 브랜치 경로와 커밋의 관계는 기존 메모이제이션 구조를 활용합니다.
- Hover 대상이 실제로 변경된 경우에만 Canvas를 다시 그립니다.
- 새 API 요청이나 주기 타이머를 추가하지 않습니다.
- 반복적인 React 전체 렌더링을 방지합니다.
- 그래프 자동 갱신 중에도 하이라이트가 정상적으로 갱신되어야 합니다.

기존 Canvas 계측과 개발자 디버그 모드를 통해 성능을 확인합니다.

## 8. 예외 처리

다음 상황에서도 기존 그래프가 정상적으로 표시되어야 합니다.

- Hover 중 브랜치가 삭제되거나 HEAD가 변경됨
- Hover 중 새로운 커밋이 자동 갱신됨
- Hover 중 과거 이력을 추가 로딩함
- 브랜치 경로가 현재 로딩 범위를 벗어남
- 해당 커밋이 여러 브랜치에 공유됨
- Hover 중 화면 방향·크기 변경
- Split view에서 저장소 순서 변경
- Split view 종료 또는 저장소 변경

강조 대상을 더 이상 확인할 수 없으면 하이라이트를 해제하고 정상 그래프로 복귀합니다.

## 9. 테스트

다음 항목을 검증합니다.

1. 브랜치 배지 Hover 시 해당 경로 강조
2. 다른 경로 노드·연결선 불투명도 50% 적용
3. 커밋 메시지·SHA·작성자 함께 강조
4. 커밋 노드와 메시지의 동일한 Hover 처리
5. 빈 공간 이동과 포인터 이탈 시 초기화
6. 같은 HEAD를 공유하는 여러 브랜치
7. 다른 브랜치와 합류하는 경로
8. Merge Commit의 다중 부모
9. 경로가 모호한 커밋의 안전한 처리
10. Actions 도넛과 릴리즈·태그 아이콘의 상태 유지
11. 기존 선택 커밋 강조 및 팝업 유지
12. 브랜치 툴팁과 Hover의 동시 동작
13. 일반 화면과 Split view의 독립 하이라이트
14. 마우스 이동 중 불필요한 레이아웃 재계산 없음
15. Hover만으로 GitHub API 요청 증가 없음
16. 자동 갱신·점진 로딩 후 경로 갱신
17. 모바일 터치 동작 회귀
18. 화면 크기 변경 및 좁은 열 표시

20. 기존 그래프·스크롤 및 Actions 상태 회귀

## 10. 작업 범위 및 지침

최신 `dev` 브랜치를 기준으로 현재 Commit Trail 구현을 확인합니다.

우선 검토할 파일은 다음과 같습니다.

- `src/Graph.tsx`
- `src/branchLabels.ts`
- `src/graphColors.ts`
- `src/model.ts`
- 관련 그래프 테스트
- 그래프 시각화 개발 명세

실제 구조에 따라 필요한 범위에서 변경합니다.

### 변경하지 않을 사항

- Git DAG 정렬 및 레인 배치 알고리즘
- 브랜치 추천·기준 브랜치 선택 정책
- GitHub API·인증·캐시
- 자동 갱신 주기
- Actions 집계 및 색상 정책
- 태그·릴리즈 아이콘 정책
- 커밋 상세 UI 디자인
- Split view 저장소 개수와 배치 정책
- URL 공유 형식
- PWA 및 배포 설정
- 프로젝트 버전

관련 명세와 기술 가이드는 실제 동작에 맞게 갱신합니다.

기존 `AGENTS.md` 지침에 따라 테스트와 빌드를 수행하고, 관련 미병합 PR을 갱신하거나 새 PR을 생성합니다.

**PR 병합 및 Production 배포는 수행하지 않습니다.**

## 최종 원칙

**Hover 하이라이트는 특정 브랜치의 Git 이력과 커밋 메시지에 집중하기 위한 기능입니다.**

선택한 경로의 노드·연결선·텍스트는 선명하게 유지하고, 다른 경로는 불투명도를 50%로 낮춥니다.

Git DAG의 실제 관계를 왜곡하지 않으며, 경로를 확정할 수 없는 경우에는 잘못된 브랜치를 강조하는 것보다 하이라이트를 생략하는 것을 우선합니다.

## 구현 및 검증 기록

- `branchTracks()`의 기존 순회에서 노드 SHA와 실제 부모 간선 키를 함께 수집한다. `graphHover.ts`가 이를 메모이제이션 가능한 경로 색인으로 만들고, `Graph.tsx`가 로컬 Hover 대상에 따라 기존 Canvas 불투명도에 배율을 적용한다. 합류·병합 경로와 레이아웃 자체는 변경하지 않는다.
- 같은 HEAD의 배지는 각 이름으로 판정하고, 여러 경로가 공유하거나 분류되지 않은 커밋은 해당 커밋만 강조한다. `(any-hover: hover)`와 이벤트의 포인터 종류를 확인하며 터치에는 하이라이트를 적용하지 않는다.
- 회귀 테스트 10개를 추가했으며 전체 소스 테스트 **444개**, TypeScript 검사와 **Production 빌드**가 통과했다. 기준 줄기에 오래된 HEAD가 남아 있는 경우의 공유 커밋 정책도 검증했다.
