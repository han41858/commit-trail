# Commit Trail — Split view 명세

## 목적과 범위

Split view는 1~32개 GitHub 저장소의 세로형 Git DAG를 가로 한 줄에 표시한다.
모바일 PWA에서는 가로 화면을 권장하며 데스크톱과 세로 화면도 지원한다.
일반 화면과 같은 그래프 엔진을 사용하고 별도 백엔드·라이브러리·Worker·Service Worker를 사용하지 않는다.

## 진입과 저장소 선택

- 선택 창을 화면 중앙에 배치한다. 두 테마의 공통 색상과 배경의 불투명도·닫기 판정은
  [공통 팝업 규칙](specification.md#3-ui-원칙)을 따른다.
- 일반 헤더의 분할 아이콘 **Split view**로 선택 창을 연다. 직전 Split view 구성이나 저장한 선택이 있으면 항목과 순서를 그대로 복원하며, 사용자가 제거한 현재 저장소를 다시 추가하지 않는다. 기존 구성이 없는 최초 선택에만 현재 저장소를 기본값으로 넣는다. URL에서 복원한 구성은 저장된 기본 선택보다 우선한다.
- 최근 방문 목록을 재사용하거나 `owner/repo`·GitHub URL을 직접 입력해 추가한다. 주소는 기존 `parseRepo`·소문자 변환·커서 보존 로직을 사용한다. 최근 항목 선택과 완성된 저장소 주소 추가는 API를 호출하지 않으며, Owner 단독 제출은 아래의 명시적 목록 조회를 실행한다.
- 선택 창 아래 **Recent repositories** 항목은 저장소 이름만 표시하며 앞쪽 화살표는 표시하지 않는다. 일반 저장소 입력창 자동완성의 최근 방문 아이콘은 유지한다.
- 중복과 32개 초과 선택을 막는다. 선택한 항목은 아래 최근 목록에서 숨기며, 위 목록에서 제거하면 아래에 최근 방문 순서대로 다시 나타난다. 32개가 선택되면 추가 가능한 최근 목록을 숨긴다.
- **선택 창 위쪽 목록**의 핸들을 마우스·터치로 드래그해 순서를 바꾼다. 키보드에서는 핸들에 포커스를 두고 ↑/↓를 사용한다. 포커스를 유지하며 변경한 위치를 스크린 리더용 상태로 알린다. 이 순서가 분할 화면의 좌우 배치·저장된 선택·공유 링크에 반영된다. 활성 분할 화면에서는 아래 헤더 핸들로 드롭 시점에만 순서를 변경한다.
- 최소 한 개를 선택해야 **Start split view**와 **Copy link** 버튼이 활성화된다. 이미 표시된 저장소의 선택·추가·제거·정렬·링크 복사는 API 요청을 발생시키지 않는다. Owner 조회와 추가 페이지 요청은 별도의 명시적 조회 동작이다.
- 선택 창은 제목·닫기와 하단 개수·**Copy link**·**Start split view**를 고정한다.
  저장소 목록·추가 입력·최근 목록을 포함한 가운데 영역만 스크롤하므로 낮은 창이나 가로 화면에서도 시작 버튼에 바로 접근할 수 있다.
  목록 드래그의 가장자리 자동 스크롤도 이 영역을 사용하며, 최근 목록을 따로 스크롤하지 않는다.
  가운데 사방의 4px 여백과 스크롤 여백은 정렬 핸들·입력창·버튼의 포커스 링을 보호한다.
  키보드 포커스는 창 안에서 이동하고, Escape·닫기·배경 클릭으로 창을 닫으면 진입 버튼으로 돌아간다.
- 활성 Split view에서도 공통 **Manage repositories** 버튼으로 기존 선택 창을 열어 저장소를 추가·제거·정렬한다. 개별 그래프 헤더에 관리/제거 버튼을 두지 않으며, 브랜치 선택·방향 전환·Options UI도 추가하지 않는다. 헤더 핸들은 기존처럼 순서 변경만 제공한다.

Owner만 입력하고 Enter 또는 **Add**를 누르면 일반 화면과 같은 조회·필터·페이지 처리를 사용하는 저장소 목록을 연다. Split view에서는 별도 테두리·제목줄·닫기 버튼 없이 기존 설정 창 본문에 검색과 체크리스트를 이어 붙이고, 중첩 대화상자가 아닌 이름 있는 영역으로 제공한다. 여러 저장소를 체크한 뒤 **Add N repositories**를 누르면 기존 선택 순서를 유지하며 체크한 순서대로 뒤에 추가한다. 체크·체크 해제·일괄 추가 자체는 API를 호출하거나 그래프를 열지 않는다.

이미 추가된 저장소는 체크된 비활성 항목과 **Already added**로 표시한다. 기존 항목과 추가 예정 항목의 합계는 최대 32개이며, 필터 변경이나 **Load more** 후에도 미확정 체크는 유지한다. 목록을 닫거나 Owner·PAT·입력 컨텍스트가 바뀌면 미확정 체크를 버린다. Owner 목록의 Escape는 목록만 닫고 설정 창을 유지한다. Owner 조회·체크만으로 저장된 구성·공유 URL·최근 방문 기록을 변경하지 않으며, 확정 추가 후 저장·공유·드래그는 기존 선택 목록 정책을 따른다. 상세 정책은 [Owner 저장소 선택](owner-repositories.md)을 따른다.

## 활성 Split view 구성 변경

- 왼쪽 책갈피 `>` 탭을 누르면 화면 밖에 숨겨진 **Return to single view → 새로고침 → Manage repositories** 버튼이 옆으로 나온다.
  기본은 접힌 상태이며 `<` 탭이나 컨트롤에 포커스가 있을 때의 Escape로 접는다.
  접힌 버튼은 키보드·접근성 탐색에서 제외하고, 접기 상태는 저장하지 않는다. 동작 줄이기 설정에서는 전환 애니메이션을 생략한다.
  관리 버튼은 Lucide `list-plus` 아이콘만 표시하며 접근성 이름·툴팁은 `Manage repositories`다.
- 펼친 상태에서 버튼을 실행하거나 커밋 노드 등 컨트롤 밖을 누르면 즉시 접는다.
  버튼을 실행하면 책갈피 탭으로 포커스를 옮기고, 바깥을 조작하면 그 조작의 선택·포커스를 유지한다.
- 기존 `MonitorSetup`을 활성 목록과 정확한 순서로 연다. 일반 화면의 제목·버튼은 `Split view`·`Start split view`, 활성 화면은 `Manage repositories`·`Apply changes`다. 직접 주소·GitHub URL·Owner 다중 선택·최근 목록·제거·드래그/키보드 정렬과 1~32개 제한을 공유한다.
- 선택·제거·정렬은 창 안의 임시 구성에만 반영한다. **Apply changes**를 눌러야 적용하며 닫기·Escape·배경 클릭은 임시 변경을 폐기한다. 창을 닫으면 책갈피 탭으로 포커스를 돌리고, 기존 커밋 상세가 열려 있어도 선택을 유지한다. Owner 목록을 여는 별도 명시적 조회 외에는 임시 구성 편집으로 그래프 API를 호출하지 않는다.
- 유지되는 저장소는 같은 `MonitorEntry`·`History`·`CommitInfoStore`·그래프 컴포넌트를 재사용한다. 커밋·브랜치·시간 방향·스크롤·유효한 고정 경로·커밋 선택·캐시와 진행 중 요청을 보존하며 열 순서·너비에 맞춰 Canvas와 상세 위치만 갱신한다. 같은 구성의 확정은 세션·URL·저장소를 변경하지 않는다.
- 추가한 저장소만 기존 초기 조회 경로로 열고 제거한 저장소는 구독·요청·재확인 대상을 정리한다. 제거된 저장소의 상세는 닫으며 늦은 응답이 새 구성의 상태나 공통 Rate Limit에 영향을 주지 않는다. 일반 화면과 공유하던 기본 열을 제거한 경우에도 요청을 취소하고, 일반 화면 복귀 시 정상 열기 경로로 다시 연다.
- 2개에서 1개로 줄여도 Split view를 유지하고 `mode=monitor`로 복원한다. 0개는 적용할 수 없다. 저장소 집합이 바뀐 적용은 history에 추가하고, 순서만 바뀌면 활성 헤더 드래그와 같이 현재 항목을 교체한다. 뒤로/앞으로 가기도 공통 저장소의 인스턴스를 재사용하며 확정한 선택만 기존 저장 키에 반영한다.
- 선택 창 열기·구성 적용·열 재정렬은 공통 자동 갱신 기한을 다시 시작하지 않는다.
  유지되는 열의 진행 중 갱신은 완료 추적에 남고, 제거된 작업의 늦은 결과는 새 완료 시각이나 Rate Limit 대기에 반영하지 않는다.

## URL 구성 공유와 복원

| URL 예시                                                                       | 동작                                    |
| ------------------------------------------------------------------------------ | --------------------------------------- |
| `/?repo=han41858/commit-trail`                                                 | 기존 단일 저장소 화면                   |
| `/?repo=han41858/commit-trail&repo=octocat/Hello-World`                        | URL 순서대로 두 저장소 분할             |
| `/?repo=han41858/commit-trail&mode=monitor`                                    | 한 저장소로 분할 모드 진입              |
| `/?repo=han41858/commit-trail&repo=octocat/Hello-World&branch=dev&branch=main` | 각 저장소를 `dev`, `main` 기준으로 복원 |
| `/?repo=han41858/commit-trail&repo=octocat/Hello-World&branch=&branch=main`    | 첫 저장소는 자동 선택, 두 번째는 `main` |

- `repo` 파라미터가 두 개 이상이거나 `mode=monitor`이면 모니터 구성을 읽는다. 기존 파서로 주소를 정규화하고 소문자 변환·중복 제거 후 앞쪽의 유효한 저장소를 최대 32개까지 사용한다. 중복·잘못된 항목 제거 후 하나만 남아도 모니터 의도를 유지하며, 유효한 항목이 전혀 없으면 빈 일반 화면을 표시한다.
- 파싱은 접근 권한을 확인하지 않는다. 실제 진입에서는 기존 모델로 각 저장소를 열고, 권한·404·네트워크 오류는 해당 열에만 표시한다. 첫 저장소가 실패해도 나머지 열은 동작하며 기존 공통 갱신으로 다시 시도한다. 부분 목록 밖의 URL·저장된 브랜치 후보에 한해서 기존 정확한 이름 조회를 재사용하며 공개 여부 확인용 추가 요청은 없다.
- 일반 화면과 활성 Split view의 선택 창에서 **Copy link**를 제공한다. 현재 선택과 순서를 반복 `repo`로 인코딩하며, 한 개일 때는 `mode=monitor`를 넣는다.
  클립보드 복사가 성공하면 **Copied!**, 거부·미지원이면 **Copy failed**를 표시하고 2초 뒤 **Copy link**로 돌아온다.
  별도 진행 문구는 표시하지 않고 처리 중에는 재클릭을 막는다. 기존 상태 영역에서도 성공·실패를 알린다.
  선택·순서가 바뀌면 피드백을 초기화하고 이전 복사의 늦은 결과를 무시한다. 복사만으로 모드를 시작하거나 현재 주소를 바꾸지 않는다.
- 공유 링크는 저장소 이름·순서·모드와 확인된 기준 브랜치를 포함한다.
  반복 `branch`는 `repo`와 인덱스로 대응하며, 미확인 중간 값은 비워 둔다. 잘못된 저장소나 중복 항목을 제거할 때 대응 브랜치도 제거한다.
  원래 주소의 다른 쿼리·해시·URL 인증 정보는 제거하며 PAT·자동 갱신 주기·디버그·스크롤 상태는 복사하지 않는다.
  **비공개 저장소·브랜치 이름도 URL에 노출된다**. 링크를 열면 수신자의 기존 PAT·인증 정책을 적용한다.
- 모드·저장소 전환은 브라우저 history에 기록하며 뒤로/앞으로 가기와 새로고침은 URL 구성을 복원한다. 저장된 선택은 URL 구성을 덮어쓰지 않는다. 기존 `?debug=1` 등 현재 탭의 부가 URL 문맥은 앱 안의 이동에서는 유지하지만 공유 링크에서는 제외한다.
- 새 탭에서 모니터 URL을 열면 첫 저장소를 기본 모델로 사용한다. 기존 일반 화면에서 진입한 경우 기본 모델·Canvas·탐색 상태를 보존하고 명시적인 URL 브랜치 변경만 적용한다. 복귀 시 그 저장소와 현재 기준 브랜치의 단일 URL로 돌아간다. 새로고침 후에는 URL의 첫 저장소가 복귀 대상이며 이전 탭의 스크롤·커밋 선택은 공유하지 않는다. URL로 복원한 선택은 로컬의 마지막 직접 선택을 덮어쓰지 않는다.
- URL 진입에도 [레이아웃과 복귀](#레이아웃과-복귀)의 창 전환 규칙을 적용한다. 탐색에는 기존 history API를 사용한다.

## 저장과 인증 경계

- localStorage 키는 `commit-trail.monitor-repositories`이며 최대 32개의 정규화된 저장소 **이름 문자열 배열만** 저장한다. PAT·토큰 일부·해시·API 응답·커밋·스크롤 위치는 포함하지 않는다.
- 잘못된 배열·주소·중복 항목은 정리한다. 저장소 접근 실패 시에도 모니터링은 현재 탭의 메모리에서 사용할 수 있다.
- 공개 여부는 최근 방문 이력의 실제 API 메타데이터 분류를 재사용한다. PAT를 쓰지 않는 직접 입력 항목은 공개 메타데이터 조회 성공 후 저장 목록에 반영한다.
- 최초 PAT 등록·교체·삭제 시 비공개 및 공개 여부를 확인할 수 없는 선택을 제거하고, 확인된 공개 선택만 유지한다. 동일 PAT 재적용과 저장된 같은 PAT 복원은 선택을 유지한다. 접근 실패만으로 목록을 삭제하지 않는다.
- 목록 자체가 접근 권한을 보장하지 않는다. 새 토큰으로 다시 조회한 비공개 저장소는 다시 선택·등록할 수 있다.
- 오래된 인증 탭은 적용 토큰과 저장 토큰의 일치 여부를 확인해 다른 인증의 비공개 선택을 표시하거나 덮어쓰지 않는다. 다른 탭의 PAT 변경 이벤트는 모니터 모드와 선택 창을 닫고 선택을 다시 읽는다. 실제 적용 토큰을 몰래 바꾸지는 않는다.
- 최근 방문 목록은 10개를 유지한다. 공개 저장소가 이 목록에서 밀려나도 선택을 복원할 수 있도록 실제 메타데이터로 확인된 공개 이름을
  `commit-trail.monitor-public-repositories`에 최대 32개의 이름 문자열 배열로 보존한다.
  별도 확인 요청을 보내거나 이 보조 키에 토큰·API 응답을 저장하지 않는다. 비공개로 바뀐 이름은 공개 분류에서 제거한다.
  제품명 변경 전의 저장 키는 읽거나 이전하지 않으므로 이전 키에만 남은 선택은 다시 설정한다.

## 레이아웃과 복귀

- 선택한 1~32개 모두를 N×1 가로 한 줄로 균등 분할한다. 1·3·4·8·16·32개도 같은 정책이며 최소 열 너비·가로 스크롤·여러 행·화면 크기나 방향에 따른 자동 개수 조정·저장소 숨김은 도입하지 않는다. 각 열은 `min-width:0`과 독립 세로 스크롤을 사용한다. 아주 좁은 화면에서 이름과 메시지를 읽기 어려운 것은 사용자가 선택한 정보 밀도로 허용한다.
- 저장소 사이의 세로 구분선은 기존 1px 간격을 유지하며, Split view에만 사용하는 `--monitor-divider`로 표시한다. 기존 `--muted` 40%와 `--bg`를 혼합해 라이트에서는 조금 어둡게, 다크에서는 조금 밝게 보이는 회색 계열을 사용한다. 헤더도 같은 간격 위치에 같은 색의 선을 이어 그리며 저장소가 하나일 때는 경계를 만들지 않는다. 공통 Border·열 크기·입력 영역은 바꾸지 않고, 선에는 포인터 입력이나 Hover 효과·크기 조절 커서를 추가하지 않는다.
- 각 영역 상단의 `owner/repo`는 밑줄이 있는 GitHub 저장소 링크이며 넓은 화면 14px·좁은 화면 13px로 표시한다. 링크의 클릭 범위는 표시된 텍스트 크기로 제한하고 열의 빈 공간·여백은 링크로 처리하지 않는다. 새 탭으로 열어 기존 분할 화면을 유지하며 `noopener noreferrer`를 적용한다. 긴 이름은 말줄임하고 링크 title과 그래프 영역의 접근성 이름에는 전체 값을 제공한다.
- 저장소 이름과 공통 복귀·새로고침·관리 버튼을 헤더에 배치한다. 이름은 각 그래프 열과 같은 순서·너비로 한 줄에 정렬하고 왼쪽의 책갈피 탭 공간만 비운다. 펼친 버튼 묶음은 이름 위에 표시되어 입력을 받으며, 관찰할 때는 접어서 이름을 확인한다. 로고·일반 헤더·일반 상태 패널을 숨긴다. 명시적으로 켠 개발자 진단 UI와 기존 PWA 업데이트 안내는 별도 기존 기능이다.
- **Start split view**와 URL 진입은 현재 앱 창의 레이아웃만 전환한다.
  Fullscreen API를 호출하거나 전체화면 이벤트를 구독하지 않는다. F11 등 사용자가 제어하는 브라우저 전체화면과 앱의 분할 상태는 독립적이다.
- 복귀 버튼은 일반 모드로 돌아간다. Escape는 드래그·브랜치 툴팁·포커스된 그래프의 고정 강조·열린 팝업 등 현재 입력을 처리하는 대상을 먼저 닫거나 해제한다. 이때 분할 모드를 함께 종료하지 않으며, 처리할 대상이 없을 때 일반 모드로 돌아간다. 경로 입력 우선순위는 [공통 명세](dag-hover-highlight.md#입력과-수명)를 따른다. 브라우저 전체화면을 켜거나 끄는 동작은 앱 모드를 바꾸지 않고, 앱에서 복귀해도 사용자가 설정한 브라우저 전체화면을 종료하지 않는다.
- 강제 화면 회전·방향 잠금은 하지 않는다. Safe Area와 기존 앱 셸의 높이를 사용하며, ResizeObserver가 각 열의 Canvas 크기를 다시 측정한다.
- 선택 UI·저장·URL 정규화·공유·세션은 `MonitorRepositories.ts`의 공통 `MONITOR_LIMIT`를 사용한다.

## 그래프와 상세

- 현재 열린 저장소가 포함되면 기존 `History`·`CommitInfoStore`·Canvas 인스턴스를 그대로 사용한다. 진입을 위해 같은 메타데이터를 다시 조회하지 않는다. 현재 브랜치·시간 방향·스크롤·선택을 유지한다.
- 추가 저장소마다 독립적인 `History`·`CommitInfoStore`를 사용하고 최신순에서 시작한다.
  기준 브랜치는 URL 지정 → 마지막 직접 선택 → `main`·`master`·GitHub 기본 브랜치 순으로 확인한다.
  모델·커밋 배열·캐시·스크롤은 저장소별로 유지한다.
- DAG 배치·레인·브랜치 배지·실제 부모 SHA 관계·태그/릴리즈 아이콘·Actions 링은 일반 화면과 같은 렌더러를 사용한다.
  경로 소유권·결정적 8색 배정과 재현성은 [공통 경로 명세](dag-hover-highlight.md)를 따른다.
  추가 저장소도 저장소 메타데이터를 받은 뒤 [공통 요청 순서](auto-refresh-and-metadata.md#93-api-호출-효율화)로 태그·릴리즈·Actions를 조회하고, 가시 커밋의 Job을 추적한다.
- [공통 반응형 표시 규칙](specification.md#3-ui-원칙)을 전체 창이 아닌 **각 열의 실제 너비**에 적용한다.
  800px 이하의 열에서 그래프 영역을 최대 50%로 제한했을 때 레인 간격 12px를 확보할 수 없으면 메시지와 그 입력 영역을 숨기고 전체 열을 그래프에 사용한다.
  너비가 800px를 넘으면 메시지와 SHA·작성자를 표시한다.
- 같은 커밋을 가리키는 브랜치는 개별 배지를 세로로 나열하고 `+N`으로 생략하지 않는다.
  묶음 높이로 겹침을 피하며 매우 큰 묶음은 그래프를 스크롤해 모든 이름을 확인한다.
- 열이 기존 좌측 기준점 48px보다 좁아지면 분할 그래프의 시작점만 해당 열 중앙으로 보정해 노드가 통째로 화면 밖으로 밀리지 않게 한다. 레인 계산·간격·행 높이는 변경하지 않고 일반 모드와 기존 너비의 분할 그래프는 그대로 유지한다. 헤더 여백도 열 너비 안으로 줄여 이름 영역과 그래프 열의 균등 너비를 유지한다.
- 행 간격은 31px다. 커밋당 버전 아이콘과 전체 태그·릴리즈 표시는 [메타데이터 명세](auto-refresh-and-metadata.md#5-git-태그-표시)를 따른다.
  월·일 날짜 구분선은 [공통 날짜 구분선 명세](date-separators.md)에 따라 각 열의 가시 너비와 메시지 앞 공간에 맞춰 표시한다.
- 연결선 판정·강조·터치 예외·선택 해제는 [공통 입력 수명](dag-hover-highlight.md#입력과-수명)을 따른다.
  선 경로는 열별 화면 구간과 좌표로 재사용한다. [불투명도 전환](dag-hover-highlight.md#불투명도)도 열마다 독립 처리하며 전환이 끝나면 추가 그리기를 멈춘다.
- 브랜치 배지는 이름끼리의 겹침만 피하고 노드·Actions 링·연결선은 덮을 수 있다. 메시지가 표시되면 메시지·SHA·작성자 열 왼쪽으로 배치와 그리기·입력 판정 범위를 제한해 글자를 가리지 않는다. 메시지가 숨겨진 열은 전체 그래프 너비를 사용한다. 표시 폭은 현재 경로 앵커와 무관하게 정해 스크롤 중 노드를 피하려고 위치나 글자 폭을 바꾸지 않는다. HEAD가 보이면 그 행에서 노드·선을 덮는 배치까지 먼저 확인하고, 다른 이름 때문에 자리가 없을 때만 경로를 따른 대체 위치를 찾는다. HEAD가 화면 밖이면 보이는 자기 경로 근처를 유지하면서 곡선을 따라간다. 짧은 경로는 우선 한 행 이내에서 보정하고, 다른 이름을 피할 공간이 없을 때만 가장 가까운 빈 위치를 사용한다. 같은 HEAD의 이름은 세로로 쌓으며 배경 약 40% 불투명도와 선명한 글자, 노드·링의 클릭·Hover 우선순위는 유지한다.
- 상세 패널은 해당 열의 중앙을 기준으로 최대 480px까지 넓혀 인접 열의 공간도 사용한다. 화면 가장자리에서는 모니터 영역과 보이는 화면의 교집합 안쪽으로 8px 여백을 두고 위치를 보정한다. 높이는 해당 영역의 65% 이내로 제한하며 Safe Area·화면 크기·모바일 키보드에 따른 보이는 화면 변화를 반영한다. 패널 상단에는 원래 열의 `owner/repo`를 표시한다.
- 상세 팝업은 화면 전체에서 하나만 열며 저장소·커밋 한 쌍을 선택한다.
  SHA가 같아도 다른 열의 커밋을 고르면 이전 팝업·노드 강조·선택 메타데이터 대상을 해제하고 새 저장소의 상세를 표시한다.
  어느 열에서든 배지·연결선을 선택하면 공용 상세를 닫지만, 다른 열에 고정된 배지·선 강조는 유지한다.
  크기·순서 변경은 Hover만 해제하고 유효한 고정 대상을 보존한다.
- 상세 패널의 DOM과 이벤트는 원래 열에 속한다. 열 밖으로 나온 부분도 클릭·터치·내부 스크롤·닫기를 지원한다.
  패널이 열려 있을 때만 위치를 관찰하며 위치 보정 자체는 API 요청을 만들지 않는다.
- 상세 내용만 내부에서 스크롤하며 닫기·GitHub 이동 버튼과 저장소 이름은 상단에 고정한다. 키보드·휠·터치 스크롤과 본문 하단의 메타데이터 추가 조회를 유지하며 다른 커밋을 고르면 본문을 맨 위로 되돌린다. 팝업 내부 클릭은 유지하고, 다른 열을 포함해 팝업 밖 빈 공간을 누르면 공통 선택을 해제한다. 메시지 뒤의 실제 글자가 없는 여백은 커밋 선택 영역에 포함하지 않는다.
- 상세를 닫으면 선택도 해제한다. 단일 화면으로 복귀할 때 추가 저장소의 팝업은 닫고 이후 재진입해도 자동으로 다시 열지 않는다. 현재 기본 저장소의 선택은 유지할 수 있으며 일반 화면의 기존 상세 배치로 복원한다. URL 구성에서 제외된 저장소의 선택도 해제한다.
- [미조회 경계의 점진 로딩](specification.md#52-api-및-로딩)은 각 열의 가로 표시 범위와 현재 화면 하단을 기준으로 한다.
  한 열의 스크롤은 다른 열을 이동시키거나 다른 열의 추가 조회를 시작하지 않는다.
  최신 위치 추적과 과거 탐색의 SHA 앵커 보정은 [공통 스크롤 규칙](auto-refresh-and-metadata.md#4-자동-갱신-시-스크롤-동작)을 열마다 적용한다.
- 모니터 대상에서 제외된 기존 일반 그래프는 DOM과 상태를 보관하면서 Canvas 렌더링·보이는 커밋 조회를 멈춘다. 종료 시 원래 단일 모드 URL과 그래프로 복귀한다.

### 커밋 상세와 하단 고정 안내의 배치

- 안내가 없으면 넓은 일반 화면(800px 초과)은 그래프 오른쪽·아래쪽 16px, 좁은 화면은 기존 `70px + safe-area`, Split view는 선택 열 중앙을 기준으로 그래프 영역 바닥 8px 위에 배치한다.
- `.app-notices`에는 화면 하단에 고정되는 안내만 둔다. 현재 PWA 업데이트 안내·디버그 진입점·디버그 로드 오류가 해당하며, 이후 추가되는 하단 안내도 이 영역에 둔다. 영역 안에 표시되는 요소는 모두 하단 안내로 측정한다. 이동 가능한 디버그 패널처럼 하단 안내가 아닌 UI는 `.app-notices` 밖의 앱 루트에 렌더링해 측정 대상에서 제외한다. 안내가 있으면 화면이나 열에 관계없이 팝업을 안내 위로 올려 최소 8px 여백을 확보한다. 가로로 겹치지 않는 열에도 같은 정책을 적용한다.
- `ResizeObserver`로 실제 렌더링된 높이와 위치를 측정한다. 줄바꿈·오류 문구·동시 표시·등장·닫힘·창 크기 변경을 반영하며 고정 안내 높이를 가정하지 않는다. 일반 화면에는 CSS 변수로 전달하고, Split view는 `monitorDetailsFrame`의 하단 경계를 안내 위로 줄여 다시 계산한다. 팝업이 올라간 만큼 최대 높이도 줄여 툴바나 그래프 상단을 넘지 않게 한다.
- 안내 변화만으로 팝업을 다시 열거나 포커스를 옮기지 않고 내부 스크롤 위치를 유지한다. 안내가 사라지면 기본 배치로 돌아간다. 안내가 위에 그려지는 기존 z-index 관계는 유지하고 실제 배치로 겹침을 방지한다.

## 활성 헤더의 순서 변경

- 각 저장소 이름 왼쪽의 작은 grip 핸들에서만 드래그를 시작한다. 저장소 이름은 기존 GitHub 링크와 말줄임을 유지한다. 핸들 title은 `Drag to reorder`이며 별도 정렬 모드나 상시 안내를 추가하지 않는다. 키보드 정렬은 기존 선택 창의 ↑/↓ 기능을 사용한다.
- 마우스는 누르면 즉시, 터치는 약 400ms 동안 누른 뒤 활성화한다. 활성화 전 6px 넘는 이동은 대기를 취소하고 기본 터치 동작을 막지 않는다. 터치 제어·선택 방지·컨텍스트 메뉴 차단은 핸들에만 적용한다.
- 드래그 중 원래 헤더만 불투명도 35%로 표시하며 다른 헤더와 그래프는 100%를 유지한다.
  불투명도 95%의 미리보기 카드에는 grip·저장소 이름·목표 순번을 넣고 2px 테두리와 그림자로 구분한다.
  카드는 마우스 포인터 옆을 따라 화면 안에서 움직인다. 터치에서는 공간이 있으면 손가락 24px 위에, 상단에서는 32px 아래에 표시한다.
  삽입할 열 경계는 헤더부터 화면 하단 Safe Area까지 이어지는 3px 선으로 표시하며, 실제 배열과 그래프 순서는 드롭할 때까지 바뀌지 않는다.
- 실제 위치가 바뀐 드롭은 이동한 헤더의 테두리·배경을 600ms 동안 강조한 뒤 복원한다. 새 드래그나 컴포넌트 종료 시 강조를 취소하며, reduced motion에서는 생략한다. 별도 타이머나 그래프 이동 애니메이션은 추가하지 않는다.
- Escape·포인터 취소·캡처 해제·blur·화면 크기 변경·세션 종료·대상 목록 교체는 확정하지 않고 취소한다. 대기 타이머·포인터 캡처·전역 리스너도 정리한다. Escape는 먼저 드래그만 취소해 현재 커밋 상세와 분할 모드를 유지한다. 같은 위치의 드롭은 URL·설정·세션을 갱신하지 않는다.
- 확정하면 `moveMonitorRepository`와 `MonitorSession.reorder`로 순서만 바꾼다.
  모델·선택·진행 중 요청·갱신 기한의 보존은 [구성 변경 규칙](#활성-split-view-구성-변경)을 따른다.
  `useRepositoryLocation.navigate`의 replace 경로로 `repo`와 대응 `branch`를 함께 이동하며 새로고침하거나 history 항목을 추가하지 않는다.
- URL 재배열에서도 같은 모델·브랜치를 재사용한다. 저장소 집합이 달라지면 추가·제거를 반영하고, URL의 요청 브랜치가 바뀐 경우에는 해당 저장소만 기존 브랜치 복원 경로를 따른다.
- 공유 URL을 열기만 해서는 기존 저장 선택을 새 구성으로 덮어쓰지 않는다. 직접 드롭하거나 선택 창에서 시작·적용을 누른 경우에만 기존 이름 배열에 순서를 저장한다. 저장 실패 시에도 현재 화면과 URL은 변경하며, 별도의 PAT·메타데이터 저장 형식은 추가하지 않는다.
- 기존 1~32개 가로 균등 분할을 유지한다. 헤더 공간 안에서 핸들을 줄이고 접힌 책갈피 탭 공간은 클리핑으로 보호한다. 극단적인 정보 밀도에서 가장자리 헤더의 조작 영역이 부족하면 기존 선택 창에서 정렬할 수 있다. 그래프 개수나 순서를 임의로 줄이지 않는다.

## 공통 갱신과 오류

일반 화면과 `RefreshLoop` 한 개를 공유하며 저장소별 주기는 없다.
[공통 실행 조건](auto-refresh-and-metadata.md#23-실행-조건)에 따라 첫 진입의 예약·버튼 활성화, 탭·네트워크 복귀와 다음 dispatch를 처리한다.
[예정 시각의 채움](auto-refresh-and-metadata.md#수동-갱신-버튼의-주기-표시)과 [완료 시각](auto-refresh-and-metadata.md#24-갱신-완료-시각)도 공통 명세를 따른다.

- `MonitorSession.refreshAll`은 자동·수동 갱신에서 이전 갱신이나 최초 로딩·기준 브랜치 변경·방향 변경이 진행 중인 저장소만 건너뛴다.
  스크롤 경계·브랜치 탐색·메타데이터 추가 조회는 갱신을 막지 않는다. 다른 저장소는 독립적으로 갱신하고 응답이 도착하는 대로 반영한다.
- 새로고침 버튼은 클릭·탭·키보드로 `RefreshLoop.refresh()`를 실행한다.
  자동 갱신을 꺼도 사용할 수 있지만 초기 로딩·한도 대기·공통 dispatch 중에는 비활성화한다.
  가운데 새로고침 문자는 회전하지 않으며 진행 상태는 접근성 이름과 `aria-busy`로 알린다.
- 각 열은 [공통 로딩 인디케이터](specification.md#3-ui-원칙)에 해당 저장소의 실제 진행 중 HTTP 요청 수만 `xN`으로 표시한다.
  다른 열과 대기 작업은 합산하지 않는다. 완료·오류·취소 시 개수를 정리한다.
- 저장소별 HTTP 풀을 사용한다. [브랜치 재확인](auto-refresh-and-metadata.md#31-브랜치-변경-감지)과
  [비인증 조회 절약 정책 및 예외](auto-refresh-and-metadata.md#94-비인증-자동-갱신)는 각 저장소에 공통으로 적용한다.
- 같은 PAT의 한도를 독립 쿼터로 취급하지 않는다. 어느 열에서든 확인한 Rate Limit 재시도 시각을 세션 전체에 즉시 적용해
  갱신·추가 경계·상세 요청을 기다리게 한다. 이미 전송된 요청은 도착할 수 있다. 인증을 바꾸면 이전 인증의 대기 시각과 늦은 결과는 무효화한다.
- 네트워크·권한·404·부분 메타데이터 오류는 해당 열에 표시하고 다른 열을 유지한다. 초기 메타데이터 실패는 다음 공통 주기에 재시도한다.
- 종료 시 추가 열의 요청·구독을 정리한다. 일반 화면에서 계속 사용하는 저장소의 작업은 유지하고 같은 `RefreshLoop`를 단일 저장소 범위로 되돌린다.

## PWA와 측정

[PWA 공통 정책](pwa.md)에 따라 정적 앱 셸만 캐시한다. API 응답·PAT를 Service Worker로 캐시하거나 백그라운드 동기화를 사용하지 않는다.
시작 주소 `/`는 일반 화면이며 저장한 선택을 다시 사용할 수 있다. 명시적 모니터 URL을 열거나 그 주소에서 새로고침하면 분할 구성을 복원한다.

HTTP 종류·상태·캐시·동시 요청·갱신·DAG·Canvas 측정과 최근 표본·진단 복사는 [개발자 진단 정책](developer-debug-mode.md)을 따른다.
Graph 요약은 마지막으로 렌더링한 그래프의 값이며, 요청·타이밍 표본은 여러 그래프에서 모인다.
저장소 이름이나 선택 목록을 측정 데이터에 포함하지 않으며 디버그가 꺼져 있으면 상세 측정용 스냅샷을 만들지 않는다.

## 검증 범위와 한계

자동 테스트는 선택·32개 제한·저장·URL·순서 변경·모델 보존·공통 갱신·오류 격리·Rate Limit 공유를 검증한다.
브라우저에서는 마우스·터치·키보드 정렬, 좁은 열의 그래프와 상세, 회전·Safe Area·포커스를 별도로 확인한다.

과거 로컬 Chromium 검증은 합성 GitHub 응답과 뷰포트·터치 에뮬레이션을 사용했다. 상세 기록은 이 문서의 Git 이력에서 확인할 수 있다.
당시 테스트 개수·합성 성능 수치는 현재 구현의 성능 보장이 아니다.
설치형 iOS/Android PWA의 롱 프레스·컨텍스트 메뉴·Safe Area, 실제 가상 키보드, 저사양 기기 성능, VoiceOver/TalkBack 낭독은 실기기에서 별도로 확인한다.

## 알려진 제약과 제외

- OS 상태 표시줄과 사용자가 직접 선택하는 브라우저 전체화면은 플랫폼 정책을 따른다.
- 320px 세로 화면의 4열은 열당 약 80px뿐이다. 노드·간선은 남지만 많은 레인의 간격과 이름·상세 텍스트 가독성은 제한된다. 가로 화면 또는 적은 저장소 수를 권장한다.
- 메모리와 요청량은 선택한 저장소의 수·크기·Actions 상태에 따라 증가한다. 기존 요청 풀은 저장소/리더 범위이며 관찰된 동시 요청 수가 전체 앱의 고정 상한은 아니다.
- 2×2·저장소별 주기/PAT·스크롤 동기화·강제 방향 전환·Actions 실행/취소·알림/소리·WebSocket/Webhook·서버 분석은 제공하지 않는다.
