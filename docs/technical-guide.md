# GitStream technical guide

Detailed usage, architecture, API behavior, development and deployment notes. See the [README](../README.md) for a product overview and screenshots.

Explore the flow of Git history. A responsive, read-only GitHub commit DAG viewer, built with React, TypeScript, Vite and Canvas 2D. No backend or database.

## Development

Use Node.js **24.x** and npm, matching [`.nvmrc`](../.nvmrc) and the package engine requirement.

```sh
npm ci
npm run dev
npm test
npm run build
```

Deploy `dist/` to any static host. Repository selection uses `?repo=owner%2Frepo` and survives refresh without server rewrites.

The bottom of Options shows the running app's build time right-aligned with a `Built at` prefix, using the browser's local date format and time zone with a consistent 24-hour `HH:mm` time. Vite embeds one UTC timestamp at build time; every device displays that same instant with its local date and zero-padded 24-hour time, without AM/PM, seconds or a time zone label. It stays fixed offline or across reloads of the same build, and the menu expands within the available viewport to keep it on one line. Unusually long values use an ellipsis, with the full localized timestamp available in the time element’s tooltip. A cached PWA keeps its previous build time until an app update is applied. Rebuilding the same commit changes the timestamp and bundle hash, so it can trigger a PWA update. The development server shows `Development`.

## Anonymous web analytics

GitStream uses Vercel Web Analytics via the official `@vercel/analytics/react` component in Production. It collects page views only; the app does not emit custom interaction events or integrate Google Analytics. Analytics is best-effort and must not block GitHub history.

The SDK's `beforeSend` filter removes URL search parameters, fragments and URL credentials from events. This includes repository and branch names in `repo` / `branch` parameters, which can be sensitive for private repositories. Only the initial page view per document is retained. Client-side changes to repository, branch, Split view order, or browser history do not create additional counted page views. No PAT, GitHub API response, commit details or selected repository names are explicitly sent as custom events.

The existing `Referrer-Policy: no-referrer` and restrictive CSP are kept; the Vercel deployment must serve the analytics script and collection route from the same origin. The app does not add cookies or user identifiers. This instrumentation is not an assertion that Vercel receives no request-level metadata; review Vercel's own documentation and applicable privacy requirements before rollout.

**Enable separately:** Open the Vercel project **git-stream → Analytics → Enable**, then deploy to Production. Confirm that the browser Network panel shows the Vercel Analytics script and page-view request, and that no `repo` or `branch` query values are sent. Compare counts when switching repositories and changing Split view order within the same document. Browser extensions and network filters may block analytics. Do not enable new custom events without a separate privacy review.

## Link previews and search metadata

`index.html` includes the product title, description, canonical URL, Open Graph metadata and an X summary card in the initial HTML. Link-preview crawlers do not need to run JavaScript or call GitHub. Both cards reuse the existing public 512×512 PNG logo at `https://git-stream-view.vercel.app/icons/icon-512.png`; the square image matches the summary-card format.

Single-repository and Split view links keep their query configuration for the app, while previews always describe GitStream. Canonical and Open Graph URLs point to the public Production root. Repository names, PATs and other query values are not inserted into metadata. `public/robots.txt` permits crawling and points to `public/sitemap.xml`, which lists only the product root.

After deployment, inspect the raw HTML at `/`, `/?repo=owner/repo` and a repeated-`repo` Split view URL without running JavaScript. Check the image URL, `/robots.txt` and `/sitemap.xml` for successful public responses and the expected content types. Vercel Preview protection and automatic noindex behavior are unchanged; use the public Production URL when validating a chat preview. Existing pasted links may retain a service's cached card until that service fetches the URL again. These metadata changes provide the card data; individual services still decide whether and how to display it.

Larger, underlined repository names align with their columns on the same header row as the timer and Return control; only the visible repository text is a link, opening its GitHub repository in a new tab. Empty header space does not navigate. Refresh and Return receive pointer input above the names. The refresh button uses the existing manual refresh flow for all selected repositories, skips busy repositories and remains usable with automatic refresh off; rate-limit cooldown or dispatch temporarily disables it. Return or Escape restores the normal graph. The app does not enter or exit browser fullscreen; use the browser's own control, such as F11, when needed. Browser fullscreen changes do not switch app modes.

Each column uses the normal graph's existing responsive text and badge rules, measured against that column's width. Narrow columns show one-line messages when the existing 12px lane-spacing threshold allows them; otherwise the graph uses the full column. Wide columns also show the short SHA and author. The single view's existing policy is unchanged.

The common `MONITOR_LIMIT` caps selection, storage, URLs and sessions at 32 after normalization and deduplication. Every selected repository remains visible in one equal-width N×1 row, without minimum column widths, horizontal scrolling, additional rows or automatic count reduction. A split column narrower than the existing 48px graph origin centers that origin so its nodes remain visible; DAG lanes, spacing and row heights are unchanged. Header padding also stays inside each column. The existing dialog scrolls internally when its selection list is long.

Already assigned node, branch, and edge colors remain stable when late references or ancestry arrive. ## Architecture and limits

`model.ts` owns data and topological lane layout; `api.ts` owns paginated REST requests; `history.ts` coordinates cancellation, encountered-parent traversal, directional pagination, deduplication, and bounded loading batches; `Graph.tsx` draws viewport nodes and intersecting edges on a DPR-aware canvas. Branch refs and lanes are separate. Commit identity is deduplicated by SHA. Parent relationships, rather than dates, determine order. Parent lanes are reused where possible, with earlier assignments preferred as pages arrive. `graphColors.ts` keeps path colors separate from lane placement: first-parent continuations and incoming merge connectors keep their path color across pagination. `branchLabels.ts` anchors labels to visible curve segments rather than only branch heads.

The canvas bounds its drawing to the viewport, but layout and edge traversal still process loaded history. No claim of unlimited history: 10,000 synthetic commits are covered by automated tests; live large-repository and 100,000-commit performance still need measurement. New history pages are requested from unresolved boundaries at or before the current viewport bottom, within horizontally visible lanes. This includes boundaries above the viewport: after a large jump, one page may still leave a path disconnected from the visible history. Layout and queue-cleanup scans keep following successor pages until the boundary moves below the viewport, reaches a root or rejoins loaded ancestry. Both display directions use the same rule without tracking prior scroll positions. This intentionally replaces the earlier rule that excluded newly inserted offscreen rows: new boundaries above the viewport are eligible, while boundaries below it remain deferred. Previously visited ranges are not accumulated. Required paths are not truncated by an arbitrary batch budget; existing concurrency, deduplication, cancellation, error and rate-limit handling still apply. Latest-follow animations do not fetch from transient viewport positions. Each History instance limits its commit request pool to sixteen concurrent HTTP requests across parent paths and activity-discovered branches. Monitor repositories use independent pools, and metadata requests use their own readers; sixteen is not an application-wide HTTP concurrency cap. A slow branch never blocks another available slot; loading continues to accept new visible boundaries, and queued work survives scrolling out of view. Identical in-flight commit queries share one request. Accepted boundary work is registered before subscribers run, and cleanup publishes the remaining queue so unresolved cursors are reconsidered without another scroll event. Empty or mismatched boundary responses keep the gap unresolved and expose Retry rather than falsely marking the path complete. Repository, direction, or token changes cancel queued and in-flight work. Fully loaded shared ancestry is not fetched again just because an API source still has additional pages. Branch-name discovery never starts commit requests. Activity discovery scans at most one metadata page and three independent histories per batch, skips already loaded heads, and pauses with a Retry branches control if it fails. Oldest-first uses API pagination metadata to avoid downloading the complete history before rendering; if last-page metadata is unavailable, it reports an error instead of scanning every page. Errors pause new automatic loading while already accepted independent requests can finish; Retry repeats failed sources without refetching successful paths. Infinite scroll is incremental loading, not an unlimited memory or performance guarantee. No offline Git history cache; private history remains visible in memory until cleared or refreshed. GitHub access depends on the browser network policy and API quota.

Missing-parent boundaries depend on commits currently loaded, not on whether their SHA was fetched earlier. If branch deletion prunes an ancestor and a later merge needs it again, traversal restores it from a valid immutable page in memory when available, without another HTTP request. An unfiltered first page pinned to a 40-character SHA must contain that commit before it enters the page cache. Empty or mismatched responses are not cached, so Retry can recover. If this validation fails for a refreshed HEAD, the previous graph, refs and HEAD remain in place for the next refresh to retry. Since-filtered activity discovery and later pages in oldest-first traversal may legitimately omit the pinned HEAD and are exempt from that check.

After a complete branch refresh, loaded paths belonging only to deleted refs are retired even if an unrelated catalog head or parent is still unknown. Current reachable ancestry and prior heads of surviving refs protect shared commits and history behind unresolved gaps; actual merge parents remain connected, while obsolete squash-merged branch paths disappear. Immutable page caches remain available if later traversal needs a retired parent. A deleted selected base still keeps its cached history and existing notice.

Activity discovery, recommendation and exact-name lookups compare late ref responses with the completed refresh version. Older results cannot restore removed names or changed heads. A complete catalog also ends old picker pagination. Parent responses whose boundary has disappeared are not integrated again; errors specific to that obsolete request are ignored, while authentication and rate-limit failures still surface. In-flight HTTP work may finish, but it cannot recreate the retired graph path.

## Deploy to Vercel

The repository includes `vercel.json`. Use Node.js **24.x**, framework **Vite**, install command `npm ci --no-audit --no-fund`, build command `npm run build`, and output directory `dist`. No backend, functions, environment variables, or build-time GitHub token are required. Never add a PAT as a `VITE_*` variable: those values would be public in the browser bundle.

### Git integration

The existing Vercel project `git-stream` is linked to `han41858/git-stream`. Keep the repository root as Root Directory, the Framework Preset as **Vite**, automatic Git deployments enabled, and the Production Branch as **main**. The GitHub default branch remains **dev**.

`vercel.json` explicitly enables Git deployments with `git.deploymentEnabled: true`. Keep Vercel's Preview Deployments enabled (`previewDeploymentsDisabled: false`). The separate `gitProviderOptions.createDeployments` option controls GitHub deployment records and is not the Vercel build switch.

- Feature branches (`feature/*` and existing `feat/*`) and `dev` receive Preview deployments through Vercel Git Integration.
- Merging a PR into `main` starts the Production build and deployment. Every feature, fix, documentation and configuration change first reaches `dev` through a PR. Only a PR from this repository's `dev` branch may target `main`; the required CI job rejects other source branches and forks. Feature, recovery and release branches must not promote directly to `main`.
- `.github/workflows/ci.yml` runs `npm ci`, `npm test`, and `npm run build` on PRs targeting `dev` or `main`, and on pushes to those branches. It reads Node.js from `.nvmrc`, caches npm downloads, and needs no additional Secrets.
- The required GitHub Actions check is **Test and build**. The Ruleset definitions in `.github/rulesets/` retain the existing protections and add this check. `dev` also requires PR branches to be up to date, so concurrent feature PRs are tested against the latest `dev`. `main` does not require an up-to-date head, but every main-targeted PR still validates its proposed merge. Its intentional file difference from `dev` is `.github/workflows/production-release.yml`. Ordinary `dev` → `main` merge commits preserve this main-only addition; do not copy it back into `dev` or merge a main-based feature branch into dev. These JSON files are definitions; changing them in Git does not update GitHub's active Rulesets automatically.
- GitHub Actions performs validation; Vercel Git Integration performs deployment. Preview builds can run alongside CI. Main's PR checks gate merging; gating production-domain assignment on post-merge checks would require separate Vercel Deployment Checks.

CI also runs on pull-request edits, including a change of target branch, so a successful main-placement check cannot be reused after retargeting to dev. Title/body edits also rerun validation; the existing concurrency rule cancels superseded runs.

Create the promotion PR only after the final development merge, using `dev` itself as its head. Merge with a merge commit, then verify that the final dev SHA is an ancestor of main. Do not squash or rebase a promotion. `.github/scripts/check-promotion.mjs` checks the PR event's base, head branch and head repository before dependencies are installed; its regression tests run with the existing release-automation tests. See the project-specific rules in [AGENTS.md](../AGENTS.md).

The shared-ancestor repair in #103/#104 is historical context. Its separate release-branch promotion path must not be reused; the corrected history now preserves the existing main-only entrypoint through normal dev → main promotions.

Use the Git deployment as the normal release path. A manual CLI deployment is an explicit exception: it can create another deployment for the same SHA, and uncommitted files can differ from that SHA. Do not add a Vercel CLI deployment step or Vercel credentials to the CI workflow.

Verify public Production access at the project's assigned production domain using an anonymous browser session or an HTTP request without Vercel authentication. Check for HTTP 200, no login redirect, working JS/CSS, and a public repository graph. A protected generated deployment URL or an authenticated fetch does not establish anonymous access.

### Production releases

Only `main` contains `.github/workflows/production-release.yml`, the **Production release** entrypoint for `deployment_status`. It calls the same-commit `.github/workflows/release.yml`, which is reusable and also exposes **Production release recovery** for manual execution. On `dev` and feature branches based on it, `release.yml` has no deployment-status trigger, so new Preview deployment events do not create skipped Production release runs. Existing run history is retained.

After a successful Vercel Production deployment, the shared workflow creates a `rel-YYYYMMDDHHmmss` tag and GitHub Release on the **deployed commit**. The timestamp uses the verified success time in **Asia/Seoul**. Release notes contain the changes, commit, production URL, and deployment links. Preview and failed deployments do not publish releases.

Vercel's GitHub deployment records must be enabled (`gitProviderOptions.createDeployments: enabled`) so GitHub receives `deployment_status` events. This records deployments; Vercel Git Integration still performs the builds. Repository-dispatch events can stay disabled. No additional Secrets or deployment CLI are needed; only the publishing job receives `contents: write`.

The workflow verifies the persisted GitHub deployment and status from the Vercel bot, the team/project dashboard URL, and that the deployed SHA belongs to `main`. Automation code is checked out from the protected default branch, not from the event's deployed commit. Runs for the same SHA are serialized. Repeated events and redeployments reuse the commit's release; failed publication reuses its tag on retry. Existing tags are never moved. A timestamp collision with another commit uses the next free second, and delayed events do not replace a newer Latest release.

To verify or recover a missed event, run **Production release recovery** from the default branch (`dev`) with its **GitHub deployment ID**. Keeping the manual workflow on the default branch preserves GitHub's Run workflow button. Dry run is enabled by default and writes no tag or release; disable it only to publish the verified successful Production deployment. Preview IDs are safe to test and are skipped. Existing historical deployments are not backfilled automatically.

The main-only entrypoint is already installed and remains on main. Changes to the shared `release.yml` and release logic first merge into dev and then promote from dev to main; do not create a separate direct-to-main configuration PR. The protected default branch (`dev`) supplies the trusted automation code, and publication uses the exact automation commit verified by the inspection job. The CI job also runs `node --test --test-isolation=none .github/scripts/*.test.mjs`; a branch-placement regression check rejects the automatic entrypoint on dev and requires it on main.

### Before publishing

```sh
npm ci --no-audit --no-fund
npm test
npm run build
npm run preview -- --port 4173
```

On the deployment, open a public repository such as `han41858/git-stream` and `angular/angular`; verify real commit data, branch selection, loading older history, direction reversal, commit links, and refreshing a `?repo=owner%2Frepo` URL. Test mobile tapping and fixed-width vertical scrolling, and desktop content-sized graph columns capped at 50% and messages capped at 50%. A fine-grained PAT can be entered in the app for a private-repository check; remove it afterwards and confirm the history clears. Check invalid repository and API-limit messages.

The current cloud environment's `api.github.com` egress policy is separate from Vercel. API requests originate in the visitor's browser. Unit tests and mocked browser checks do not establish that live GitHub access works; live API and private-repository validation remain release checks.

Hashed Vite assets use immutable caching; the HTML keeps Vercel's default caching. Security headers disable framing and sensitive device permissions, prevent MIME sniffing, and omit the referrer. A Content Security Policy allows scripts and PWA shell requests from this site and GitHub API requests to `api.github.com`, so a stored token cannot be sent elsewhere by injected code. Query-based navigation does not require a catch-all rewrite.

Vercel GitHub bot comments are disabled through the project’s commit/PR comment settings and `github.silent` in `vercel.json`.

Month separators span the viewport with `YYYY.MM` above the line at the right. They group committer timestamps (or valid author timestamps when unavailable) by year and month in the browser's local time zone. The selected branch's loaded first-parent history confirms month boundaries; when its tip is not loaded, the available timeline supplies that context. A partial oldest month still waits for older context, so an unrelated old branch cannot make a partial base month complete.

For each confirmed month, the line attaches to the earliest timestamp among **all loaded commits**, including merged side branches. Loading an earlier candidate moves the line to that commit; equal timestamps use a stable SHA tie-break. Older and Newer views retain the same anchor while its position reverses with the graph. Single and split views share this rule. Changing the current calendar month does not add a separator without a commit in that month; commit ordering and API requests are unchanged.


## Automatic updates and metadata

Split view starts with `RefreshLoop.waitingForInitialLoad`: no automatic timeout or visible sweep is armed until every initial history and metadata operation has settled. The refresh control is disabled during that phase. Success and failure both finish initial loading; the first deadline is a full interval after settlement. Entering Split view with an already loaded primary still waits for any new columns. Later dispatch deadlines, independent repository responses and completion timestamps retain their existing policies.

`MonitorSession.settled` publishes readiness changes from every repository, including final pending-source cleanup and metadata jobs that finish after the initial open task. A failed request still settles: error information remains visible while the shared countdown and manual refresh become usable again. When the primary history has an error, common refresh uses its existing retry path just like secondary histories, retrying the failed source without a browser reload. No polling timer or healthy-cycle API request is added.

The visible fill is aligned after DOM commit by anchoring its CSS animation start time to the same `nextAt` deadline, using the document's monotonic animation clock. Visibility and online events realign it without polling or API calls. Unrelated renders do not restart the animation; the hidden single-view sweep is inactive during Split view. Automatic callbacks also recheck initialization, enabled state and the latest deadline before dispatching.

The graph shows at most one version icon per commit: 🚀 when any release exists, otherwise 🏷️ when any tag exists, and no icon when neither exists. Releases take priority even if additional tags are attached. This rule uses the same rendering, hit-testing and tooltip path in single and Split view on desktop and mobile, including after metadata refreshes. The retained icon keeps its size and position with no empty slot for a hidden tag. Clicking or tapping it opens the existing commit details with every tag name/link, release name/link and associated tag intact. `CommitInfo`, API requests, caching and refresh scheduling are unchanged.

In newest-first mode, a reader at the latest edge follows newer commits arriving from independent branch discovery as well as refreshes. A short eased scroll reveals new commits, continues across overlapping branch responses, stops on direct scroll input, and respects reduced motion. Reading older history keeps the current commit anchored; older pagination and unchanged metadata do not snap the viewport. The refresh button updates the current repository. Options provides a single automatic refresh switch and interval (authenticated: 30 seconds, 1 minute or 5 minutes; anonymous: 1 or 5 minutes). Defaults are 1 minute with an applied token and 5 minutes without. Hidden/offline tabs pause; overdue updates resume on return. `RefreshLoop.lastCompletedAt` records the end of an attempted refresh regardless of success; errors and retry deadlines are separate. Single-view history and metadata must both settle, including when one fails. Split view records the last completion among only the repository jobs newly started in that dispatch; jobs already busy from an earlier cycle are excluded, and a dispatch starting no jobs records no completion. Each repository still renders independently. Deferred completion tracking does not hold the shared timer: single-view deadlines still follow work completion, while split deadlines still follow dispatch, so faster repositories can refresh on subsequent ticks. Initial timestamps wait for initial work to settle, and discarded sessions, scope changes and stopped loops ignore late completions. No additional timers, API requests or cache changes are introduced. The footer keeps the existing completion-time or error/backoff display.

Tags (🏷️), GitHub Releases (🚀) and Actions rings augment commits without changing their coordinates. Commit-level Actions rings use green when every workflow is completed, at least one result is success, and every result is success or skipped; a success mixed with skipped workflows is therefore green. All-skipped runs and success mixed with neutral, cancelled, action_required, stale or unknown results remain gray. Running job progress is yellow, failure/timeout/startup failure is red, and waiting or all-cancelled results keep their existing gray states. This aggregate-only policy applies to every workflow name and to both single and Split view; original conclusions, individual detail icons, job counts/progress, API requests and caching are unchanged. There is no purple other-result category. Active runs retain priority; after they finish, any known failure remains red even alongside unknown results. Individual workflow icons and API result names remain available in the detail panel. Select a commit for version links, consistent 16px outline SVG workflow status icons before their names (green check, yellow spinner, gray waiting clock, red failure/timeout, and distinct cancel/skip/warning/unknown shapes), elapsed duration, attempts and known job counts. Active durations update locally; completed durations freeze at the final API status update without additional requests. Each workflow uses one row: status icon, linked name, optional job count, then elapsed time and Attempt. Elapsed time and Attempt use smaller muted text aligned to the right without wrapping; the Elapsed label remains in their tooltip. Long names use an ellipsis within the available width and retain a full-name tooltip and the original link. This layout is shared by single and Split view. Active workflow rows show completed/total job counts after the name; unconfirmed counts show ?/?, and completed workflows omit the count. The Actions heading shows a compact yellow completed/total summary such as 48/51 jobs (94%), without a separate status line or progress bar, alongside total elapsed time from the earliest workflow start to now or the final run status update when all runs finish. Overlapping workflows share elapsed wall time. Percentages count completed jobs, not elapsed time; incomplete or unconfirmed totals use a rotating graph donut without a percentage. Rotation is limited to visible running commits, pauses in hidden tabs, respects reduced motion and adds no API calls or canvas redraw loop. A Release icon does not mean a deployment completed. Actions access optionally needs **Actions: Read-only**. Missing metadata permissions do not clear the graph.

The Token popup maps features to required read permissions and checks the applied token against the selected repository. It validates token identity, then probes Contents, Pull requests and Actions separately; Recheck repeats the checks. Edited tokens are checked after Apply, and results are not persisted. ✅ marks available access, 🚫 marks blocked access or an invalid token, and unverified/rate-limited states remain distinct. The popup omits login IDs and repeated repository labels. Checks report repository feature access rather than the complete token grant list. Create token is a prominent button and closes the token popup when opening GitHub. Opening the token popup dismisses prior API-limit guidance without clearing the retry deadline. Token, Options, branch and commit-detail popups close on outside presses or Escape; interaction inside a popup keeps it open. Closing commit details also clears the selection and restores the node and Actions ring to their usual sizes, while keeping fetched metadata cached.

Conditional ETag reads reuse unchanged data. Known commits are reused. For a commit with active workflows, missing completed-job snapshots are filled once so aggregate progress has every denominator; complete final snapshots are cached. Finished commits stop job reads, while recent workflow runs can reactivate tracking on a new attempt. Reference deletion requires a complete branch catalog. Unreachable commits are removed only when ancestry can be established; partial history is retained without a separate footer notice. Tag and release names share rows with their icons, and matching release names/versions are shown once. Version/run history is loaded in bounded pages: scrolling the commit panel continues version catalogs, the selected SHA’s runs and unfinished job pages. A short panel loads one initial continuation; further pages follow wheel, touch or keyboard scrolling without a button or repeated completed-page requests. See [the extension specification](auto-refresh-and-metadata.md).

## Developer diagnostics

In development, press **Ctrl + Shift + D** to open the debug panel. On any build, use `/?repo=owner%2Frepository&debug=1` to enable the small debug entry button. Closing the panel keeps measurements running; **Disable debug** stops and clears them.

In the installed PWA, enter `:debug` in the existing repository field and press Enter or Explore. This also works on the web. It opens diagnostics and restores the current repository field without reloading the page, changing the URL, or issuing API requests. It keeps existing measurements if already enabled; otherwise it starts a new in-memory debug session. No debug button is shown by default, and the command needs to be entered again after a fresh launch or reload unless `?debug=1` is present.

The panel separates HTTP/cache/quota observations, initial/manual/automatic refreshes, DAG layout and Canvas drawing. Each category retains its latest 20 samples in memory. **Copy diagnostics** exports numeric, sanitized JSON; details and refresh summaries also appear in DevTools Console. No extra API calls, external telemetry or persisted diagnostics are added. See [the developer debug specification](developer-debug-mode.md) for measurement boundaries and limitations.

## Installable web app (PWA)

GitStream can be installed from a supported browser or added to the iOS home screen. It opens in standalone mode with the existing graph and controls. No install banner is shown. The app identity and launcher start at `/`; repository links still use `?repo=`.

Production builds use `vite-plugin-pwa` to cache the static app shell, including lazy UI assets. **GitHub API responses, private history and PATs are never stored in Service Worker Cache Storage.** GitHub still needs a network connection. The existing browser localStorage token policy is unchanged. Service Workers require HTTPS (localhost works for development verification); Vite's dev server does not register the production worker.

A ready app version shows **Update app** and **Later** at the bottom right, with 12px edge spacing or the larger safe-area inset. When present, the debug entry or load-error notice stacks 8px above it without raising the update prompt; the debug position without an update stays unchanged. Applying reloads the consenting window after the new worker activates, preserving its URL. Another tab's approval does not force the current tab to reload. Failed downloads leave the installed shell available. Static cache cleanup happens on activation. Preview and Production have separate origins, workers, caches and installations; use the stable Production domain for normal installation.

See [the PWA specification and verification checklist](pwa.md) for cache boundaries, update behavior, CSP changes and physical-device checks that still need a release environment.
