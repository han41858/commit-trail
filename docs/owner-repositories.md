# Owner 기반 저장소 선택

## 목적과 입력

GitHub 사용자나 조직의 이름만 알고 있을 때 기존 저장소 입력창에서 저장소를 찾아 선택한다. 일반 화면과 Split view의 저장소 추가 입력은 같은 조회 모델과 목록 UI를 사용한다. 저장소 선택 이후에는 각각 기존 그래프 진입 또는 선택 목록 추가 흐름을 실행한다.

| 입력 | Enter·기존 실행 버튼 |
| --- | --- |
| `han41858` | 해당 Owner의 저장소 목록 조회 |
| `han41858/commit-trail` | 목록 조회 없이 기존 저장소 열기·추가 |
| `https://github.com/han41858/commit-trail` | 기존 URL 파싱 후 저장소 열기·추가 |
| 빈 문자열·잘못된 값 | 기존 빈 입력·검증 처리 |

Owner는 앞뒤 공백을 제거하고 소문자로 정규화한 GitHub login이다. 영문·숫자와 내부의 단일 하이픈을 허용하며 길이는 1–39자다. 시작·끝 하이픈, 연속 하이픈, Owner 프로필 URL과 `owner/`는 새 Owner 입력 형식에 포함하지 않는다. 기존 저장소 URL·`.git`·끝 슬래시 파싱과 저장소 이름 정규화는 그대로 유지한다.

Owner 조회는 Enter 또는 기존 실행 버튼으로만 시작한다. 입력 중, Owner 이름 편집 중, 목록의 필터 변경 중에는 요청하지 않는다. 로컬 최근 저장소 추천과 그 키보드 선택은 기존 동작을 유지한다. 명시적으로 선택한 최근 항목은 그 저장소를 연다.

Owner 조회·오류·목록 닫기는 현재 그래프·기준 브랜치·URL을 바꾸지 않는다. 선택 후 기존 진입이 성공했을 때만 기존 최근 방문·브랜치 복원 정책이 적용된다. Owner를 조회하거나 목록을 필터링한 행위 자체는 방문 기록을 만들지 않는다.

## 목록과 선택

- 기존 입력 바로 아래에 표시한다. 전체 화면이나 새 설정·인증 창을 만들지 않는다.
- 저장소 이름을 주요 정보로, **Public**·**Private** 여부와 선택적인 한 줄 설명을 보조 정보로 표시한다. 긴 설명은 말줄임한다.
- 현재 로딩된 항목을 `pushed_at` 내림차순, 같은 시각이면 저장소 이름의 안정적인 순서로 정렬한다. Push 시각이 없는 항목은 뒤에 둔다. 정렬 선택 UI는 없다.
- 목록의 별도 검색 입력은 저장소 이름의 대소문자 무관 부분 일치를 사용한다. 현재 로딩된 항목만 검색하며, 추가 페이지가 도착하면 같은 검색어에 반영한다.
- 항목 클릭·탭 또는 방향키와 Enter로 선택한다. Escape·목록 바깥 클릭은 목록을 닫는다. Owner 입력이나 입력 컨텍스트가 바뀌면 이전 목록을 닫는다.
- 일반 화면의 선택은 기존 저장소 열기로 이어진다. Split view에서는 한 항목을 기존 선택 목록에 추가하며, 중복·32개 제한·기존 순서·드래그·공유 URL 정책을 유지한다.
- Split view에서 이미 선택한 저장소는 다시 추가하지 않는다. Owner 목록의 Escape는 목록만 닫고 설정 창은 유지한다.

## 공개·인증 결과

공개 소스는 `GET /users/{owner}/repos`, 인증 소스는 적용된 PAT의 `GET /user/repos`를 사용한다. 공개 요청은 `type=owner`, 인증 요청은 `affiliation=owner,collaborator,organization_member`를 사용한다. 두 요청은 최근 Push 순서, 내림차순, 페이지당 100개를 지정한다. 조직 이름도 공개 Owner 목록 경로로 조회하며 별도 Owner 프로필 확인 요청은 추가하지 않는다. 공개 요청은 PAT가 적용되어 있어도 인증 헤더를 보내지 않아, 잘못된 PAT 때문에 공개 탐색까지 실패하지 않도록 한다.

인증 목록에는 본인·협업자·조직 구성원으로 접근 가능한 여러 Owner의 저장소가 섞일 수 있다. 응답의 실제 `owner.login`을 요청 Owner와 대소문자 무관하게 비교해 일치하는 항목만 반영한다. 동일 저장소는 저장소 ID로 중복 제거하며, 인증 여부만으로 Private라고 추정하지 않는다. GitHub가 실제 반환한 공개 여부와 저장소 정보만 표시한다.

| 인증 상태 | 공개 목록 | 인증 목록 |
| --- | --- | --- |
| PAT 없음 | 익명 조회 | 요청하지 않음 |
| 유효한 PAT | 익명 조회 | 해당 PAT로 반환된 저장소만 추가 |
| 접근 범위가 제한된 PAT | 익명 조회 | 허용된 범위만 추가 |
| 유효하지 않은 PAT | 성공한 공개 결과 유지 | 인증 오류 표시 |

Fine-grained PAT의 저장소 허용 범위와 Metadata 읽기 접근이 적용된다. 이 기능을 위해 별도 권한·계정 연결·OAuth를 요구하지 않으며, 기존 Token 화면과 PAT 저장 정책을 유지한다. 목록에 없다는 사실만으로 저장소의 부재나 접근 불가를 확정하지 않는다.

## 페이지와 오류

공개·인증 소스의 로딩·다음 페이지·오류·재시도 시각을 독립적으로 관리한다. 두 소스는 동시에 시작할 수 있고 먼저 끝난 소스부터 화면에 반영한다. 한 소스의 실패가 다른 소스의 성공을 지우지 않는다.

- 첫 페이지 이후에는 **Load more**를 명시적으로 눌렀을 때만 추가 조회한다. 각 정상 소스의 다음 페이지를 한 번씩 진행하며 전체 목록을 자동으로 끝까지 스캔하지 않는다.
- GitHub가 다음 페이지를 제공하면 인증 페이지에 요청 Owner가 한 개도 없어도 계속 조회할 수 있다. 이 경우 빈 페이지를 전체 결과 없음으로 확정하지 않는다.
- 추가 페이지 실패 시 이미 표시된 항목은 유지한다. Retry는 실패한 조회를 재시도하며 정상 결과를 다시 읽기 위해 초기화하지 않는다.
- API Rate Limit의 재시도 시각은 목록을 닫거나 다른 Owner를 조회해도 소스별로 유지하며, 그 전에 해당 소스를 다시 요청하지 않는다. 네트워크·인증·접근 오류는 기존 GitHub 오류 처리와 같은 원칙으로 안내한다.
- 전체 빈 결과와 현재 로딩된 항목에서의 필터 불일치를 구분한다. 다음 페이지가 있으면 현재 목록만 검색했다는 점과 추가 조회 가능성을 표시한다.
- 공개 목록 없음, 조회 가능한 항목 없음, Owner 조회 오류, 인증 조회 오류를 구분한다. 오류로 아직 읽지 못한 Private 저장소의 존재나 정보를 추정하지 않는다.

불필요한 토스트는 추가하지 않는다. 로딩에는 기존 인디케이터를 활용한다. Owner 목록의 실제 HTTP 요청도 공통 요청 수에 포함하며, 대기열은 진행 요청 수에서 제외한다. `/users`·`/user` 목록 요청을 특정 저장소의 요청으로 분류하지 않으므로 Split view 열별 요청 집계를 오염시키지 않는다.

## 메모리 캐시와 수명

`OwnerRepositories`가 두 입력 UI의 조회 상태를 공유하고 기존 `GitHubReader`의 요청·취소·집계 경로를 재사용한다. 성공한 소스의 페이지 결과는 첫 페이지 완료 시점부터 메모리에서 60초 동안 재사용하고, 최근 사용한 최대 10개 Owner를 보관한다. 추가 페이지 로딩은 캐시 만료 시각을 연장하지 않는다. 같은 이름의 대소문자 차이는 같은 캐시 대상으로 처리한다. 영구 Owner 기록·새 localStorage 키·Service Worker API 캐시는 만들지 않는다.

- 유효한 캐시로 다시 열면 이미 로딩한 결과와 페이지 상태를 재사용한다. 캐시가 없거나 만료됐으면 다음 명시적 제출에서 정상 조회한다.
- PAT 추가·변경·삭제 시 표시 중인 목록과 캐시를 무효화한다. 이전 PAT로 받은 Private 이름이 새 인증 컨텍스트에 남지 않는다.
- 다른 탭에서 PAT 저장이 변경되면 Owner 목록을 닫고 인증 조회 컨텍스트를 비운다. 이 탭에서 PAT를 명시적으로 다시 적용할 때까지 Owner 인증 목록은 조회하지 않는다. 기존 그래프의 인증 동작은 바꾸지 않는다.
- 목록 닫기·다른 Owner 제출·입력 컨텍스트 종료는 진행 중 요청을 취소하고, 취소를 무시한 늦은 응답도 현재 목록에 반영하지 않는다. 닫기 전에 완료된 유효한 캐시는 재사용할 수 있다.
- 입력이 바뀌었다는 이유로 다음 Owner를 자동 조회하지 않는다. 명시적 제출을 기다린다.

## 접근성과 반응형

검색 입력과 목록에 접근성 이름을 제공하고, 현재 키보드 항목·선택·로딩 상태를 전달한다. 목록 내부 키보드 조작이 상위 폼을 다시 제출하거나 Split view 설정을 함께 닫지 않게 처리한다. 목록 종료 후 기존 입력으로 돌아가서 편집할 수 있다.

기존 테마 색상과 컨트롤 스타일을 사용한다. 좁은 화면에서는 사용 가능한 뷰포트 높이와 스크롤 영역 안에 목록을 제한하고, 긴 이름·설명 때문에 가로로 넘치지 않도록 한다. Split view 설정에서는 기존 고정 하단 액션과 중간 스크롤 영역을 유지한다. 추가 모달·애니메이션·기기별 입력 정책은 만들지 않는다.

## 구현과 검증 기준

- `src/repoInput.ts`: Owner 입력 판별과 기존 입력 정규화.
- `src/OwnerRepositories.ts`: 공개·인증 조회, 페이지·오류·메모리 캐시와 인증 수명.
- `src/OwnerRepositoryPicker.tsx`: 공통 필터·목록·선택·로딩·오류·추가 페이지 UI.
- `src/useOwnerRepositoryPicker.ts`: 두 입력의 명시적 제출·닫기·입력 컨텍스트 연결.
- `src/RepositoryInput.tsx`, `src/MonitorSetup.tsx`: 기존 직접 입력·최근 추천·저장소 진입 또는 추가 연결.
- `src/main.tsx`: 앱 수명의 조회 모델과 기존 PAT 변경 경로 연결.

회귀 검증은 Owner/직접 주소/URL/잘못된 입력의 분기, 익명·제한 PAT·잘못된 PAT, 중복 제거·정렬·Owner 필터·독립 페이지·오류 보존·재시도, 취소·늦은 응답·캐시 재사용·PAT 변경 시 Private 제거를 포함한다. UI는 일반/Split view의 키보드·터치·외부 닫기·필터 무요청·중복·32개 제한과 기존 요청 집계를 확인한다. 브라우저 fixture·실제 GitHub·실기기 검증 범위는 구분해 보고한다.

## 범위에서 제외

입력 중 원격 자동완성, Owner 즐겨찾기·영구 검색 이력, 저장소 다중 선택, Star·언어 기반 추천, GraphQL, 새 서버·데이터베이스·의존성·인증 화면은 추가하지 않는다. 기존 DAG·브랜치·갱신·PWA 정책은 유지한다.
