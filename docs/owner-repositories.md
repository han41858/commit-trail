# Owner 기반 저장소 선택

## 목적과 입력

GitHub 사용자나 조직의 이름만 알고 있을 때 기존 저장소 입력창에서 저장소를 찾아 선택한다. 일반 화면과 Split view의 저장소 추가 입력은 같은 조회 모델·필터·페이지 처리를 사용한다. 일반 화면은 한 저장소를 선택하면 즉시 기존 그래프 진입을 실행하고, Split view는 체크한 여러 저장소를 명시적으로 기존 선택 목록에 추가한다.

| 입력                                       | Enter·기존 실행 버튼                 |
| ------------------------------------------ | ------------------------------------ |
| `han41858`                                 | 해당 Owner의 저장소 목록 조회        |
| `han41858/commit-trail`                    | 목록 조회 없이 기존 저장소 열기·추가 |
| `https://github.com/han41858/commit-trail` | 기존 URL 파싱 후 저장소 열기·추가    |
| 빈 문자열·잘못된 값                        | 기존 빈 입력·검증 처리               |

Owner는 앞뒤 공백을 제거하고 소문자로 정규화한 GitHub login으로 판별한다.
영문·숫자와 내부의 단일 하이픈으로 이루어진 1–39자만 허용한다.
시작·끝 하이픈, 연속 하이픈, Owner 프로필 URL과 `owner/`는 Owner 단독 입력으로 처리하지 않는다.
기존 저장소 URL·`.git`·끝 슬래시 파싱과 저장소 이름 정규화는 그대로 유지한다.

Owner 조회는 Enter 또는 기존 실행 버튼으로만 시작한다. 입력하거나 편집하는 동안에는 요청하지 않는다.
같은 입력창의 로컬 추천과 키보드 선택은 [최근 방문 저장소 명세](recent-repositories.md#입력목록접근성)를 따른다.
명시적으로 선택한 최근 항목은 Owner 목록을 조회하지 않고 그 저장소를 연다.

Owner 조회·오류·목록 닫기는 현재 그래프·기준 브랜치·URL을 바꾸지 않는다.
Owner 조회나 목록 필터링은 방문 기록을 만들지 않는다. 일반 화면에서 선택한 저장소는 기존 경로로 열며,
방문 기록과 브랜치 복원은 [최근 방문 저장소 명세](recent-repositories.md#데이터와-성공-기록)를 따른다.

## 목록과 선택

- 기존 입력 바로 아래에 표시한다. 전체 화면이나 새 설정·인증 창을 만들지 않는다.
- 일반 화면에서는 입력 아래 드롭다운으로 표시한다. Split view 설정에서는 별도 팝업 테두리·닫기 버튼 없이 기존 본문에 필터와 목록을 이어 붙이며, 접근성 트리에서도 중첩 대화상자가 아닌 이름 있는 영역으로 제공한다. 조회·검색·목록 종료 정책은 두 화면이 공유하며, 선택 확정 방식은 아래와 같이 구분한다.
- 두 화면 모두 제목은 `Repositories for owner (N)`으로 표시한다. N은 현재까지 로딩된 통합 저장소 수이며 필터 결과 개수는 아니다. 공개·인증 소스 중 다음 페이지가 남아 있으면 `(N+)`, 다음 페이지가 없으면 `(N)`으로 표시한다. 별도의 `N loaded`·정렬 기준 안내는 표시하지 않는다.
- 저장소 이름을 주요 정보로, **Public**·**Private** 여부와 선택적인 한 줄 설명을 보조 정보로 표시한다. 긴 설명은 말줄임한다.
- 현재 로딩된 항목을 저장소 이름의 대소문자 무관 오름차순으로 정렬하고, 같은 이름이면 저장소 ID로 안정적으로 정렬한다. 정렬 선택 UI는 없다.
- 목록의 별도 검색 입력은 저장소 이름의 대소문자 무관 부분 일치를 사용한다. 현재 로딩된 항목만 검색하며, 추가 페이지가 도착하면 같은 검색어에 반영한다.
- 일반 화면은 항목 클릭·탭 또는 방향키와 Enter로 한 저장소를 선택해 바로 연다.
- Split view는 인라인 체크리스트에서 체크박스 또는 저장소 이름·설명·행 여백을 눌러 체크 상태를 전환한다.
  행을 눌러도 목록과 설정 창은 유지한다. 하나만 체크하면 **Add 1 repository**, 여러 개를 체크하면 **Add N repositories**로 추가한다.
  체크·체크 해제·추가 확정 자체는 그래프를 열거나 API를 호출하지 않는다.
  기존 선택 목록의 순서는 유지하고 새 항목은 체크한 순서로 뒤에 붙인다.
- Split view에 이미 추가된 저장소는 체크된 비활성 항목과 **Already added**로 표시한다. 해당 목록에서 해제하거나 중복 추가하지 않는다. 기존 항목과 추가 예정 항목의 합계는 최대 32개이며, 한도에 도달해도 추가 예정 항목을 해제할 수 있다.
- 필터를 바꾸거나 페이지를 추가해도 체크한 항목은 유지한다. 필터 밖으로 숨겨진 체크도 추가 예정 개수에 포함한다.
  체크만으로 기존 선택 목록·저장된 구성·공유 URL·최근 방문 기록은 바뀌지 않는다.
  명시적으로 추가한 뒤의 저장·공유·드래그는 [Split view 명세](monitor-mode.md#진입과-저장소-선택)를 따른다.
- Escape·목록 바깥 클릭·목록 바깥으로의 포커스 이동·입력 컨텍스트 종료 시 목록을 닫고 미확정 체크를 버린다.
  입력값이 조회한 Owner와 다르게 바뀌거나 PAT가 변경돼도 목록을 닫고 미확정 체크를 버린다.
  Owner 목록의 Escape는 목록만 닫고 Split view 설정 창은 유지한다.

## 공개·인증 결과

공개 소스는 `GET /users/{owner}/repos`, 인증 소스는 적용된 PAT의 `GET /user/repos`를 사용한다. 공개 요청은 `type=owner`, 인증 요청은 `affiliation=owner,collaborator,organization_member`를 사용한다. 두 요청은 `sort=full_name&direction=asc`로 이름 오름차순, 페이지당 100개를 지정한다. 조직 이름도 공개 Owner 목록 경로로 조회하며 별도 Owner 프로필 확인 요청은 추가하지 않는다. 공개 요청은 PAT가 적용되어 있어도 인증 헤더를 보내지 않아, 잘못된 PAT 때문에 공개 탐색까지 실패하지 않도록 한다.

인증 목록에는 본인·협업자·조직 구성원으로 접근 가능한 여러 Owner의 저장소가 섞일 수 있다. 응답의 실제 `owner.login`을 요청 Owner와 대소문자 무관하게 비교해 일치하는 항목만 반영한다. 동일 저장소는 저장소 ID로 중복 제거하며, 인증 여부만으로 Private라고 추정하지 않는다. GitHub가 실제 반환한 공개 여부와 저장소 정보만 표시한다.

| 인증 상태              | 공개 목록             | 인증 목록                       |
| ---------------------- | --------------------- | ------------------------------- |
| PAT 없음               | 익명 조회             | 요청하지 않음                   |
| 유효한 PAT             | 익명 조회             | 해당 PAT로 반환된 저장소만 추가 |
| 접근 범위가 제한된 PAT | 익명 조회             | 허용된 범위만 추가              |
| 유효하지 않은 PAT      | 성공한 공개 결과 유지 | 인증 오류 표시                  |

Fine-grained PAT의 저장소 허용 범위와 Metadata 읽기 접근이 적용된다. 이 기능을 위해 별도 권한·계정 연결·OAuth를 요구하지 않으며, 기존 Token 화면과 PAT 저장 정책을 유지한다. 목록에 없다는 사실만으로 저장소의 부재나 접근 불가를 확정하지 않는다.

## 페이지와 오류

공개·인증 소스의 페이지·캐시·오류·재시도 시각은 독립적으로 관리하되, 목록은 한 번의 조회 동작을 기준으로 통합해 표시한다. 최초 조회에서는 공개·인증 첫 페이지를 병렬 요청하고, 해당 동작에서 실제로 시작한 요청이 모두 성공 또는 실패로 종료되면 성공한 결과를 합쳐 중복 제거·정렬한 목록을 한 번에 반영한다. PAT가 없으면 공개 요청 하나의 종료 후 표시한다. 유효한 캐시로 충족된 소스는 다시 요청하지 않는다.

일반 화면과 Split view는 같은 추가 조회 규칙을 적용한다.

- 목록 하단 120px 이내에서 사용자가 아래로 스크롤하거나 **Load more**를 누르면 `loadMore()`를 한 번 호출한다.
  정상 소스의 다음 페이지와 대기가 끝난 오류 소스의 실패 페이지를 한 배치로 요청한다.
  첫 페이지 실패도 같은 버튼으로 재시도하며, 별도 Retry 버튼이나 `retry()` 메서드는 사용하지 않는다.
  로딩 중에는 버튼과 스크롤이 겹쳐도 중복 배치를 시작하지 않는다.
- 300ms 동안 새 아래 방향 입력이 없을 때 다음 스크롤 동작으로 구분하고, 한 동작에서는 추가 조회를 한 배치로 제한한다.
  인증 페이지에 해당 Owner가 없거나 항목이 적어서 스크롤바가 없어도 새 아래 방향 휠·터치 동작으로 다음 배치를 요청할 수 있다.
  응답 완료나 목록 크기 변경만으로 연속 조회하지 않는다.
- 다음 페이지나 오류 소스가 있거나 배치를 로딩 중이면 같은 스크롤 영역의 마지막 항목 바로 뒤에 **Load more**를 표시한다.
  버튼 문구는 고정하고, 로딩 중이거나 모든 조회 대상이 Rate Limit 대기 중이면 비활성화한다.
  로딩과 오류는 기존 상태 영역으로 알린다. 별도 재시도 문구나 카운트다운을 표시하지 않으며 힌트를 live region으로 만들지 않는다.
  버튼은 기존 힌트·오류 영역과 `aria-describedby`로 연결한다.
  필터 사용 중에는 추가 조회를 막고 버튼을 숨기며, 다음 페이지나 오류가 있으면 **Clear filter to load more**로 안내한다.
- 추가 페이지를 로딩할 때는 기존 목록을 유지하고, 해당 배치에서 시작한 요청이 모두 끝난 뒤 통합 결과를 반영한다.
  실패해도 이미 표시된 항목을 유지한다. 먼저 도착한 소스의 항목만 반영하거나 여러 API 요청을 하나로 합치지 않는다.
- Owner 필터 적용 전 원본 응답이 100개 미만이거나 응답의 Link에 다음 페이지가 없으면 해당 소스를 완료로 처리한다.
  오류가 없는 완료 소스는 다시 요청하지 않는다. 다음 페이지가 남아 있으면 현재 인증 페이지에 해당 Owner의 항목이 없더라도
  추가 조회를 허용하며, 빈 페이지를 전체 결과 없음으로 확정하지 않는다.
- 공개 조회 성공·인증 조회 실패이면 공개 결과와 인증 오류를 함께 표시한다. 한 소스의 실패가 다른 소스의 성공을 지우지 않는다.
- API Rate Limit의 재시도 시각은 목록을 닫거나 다른 Owner를 조회해도 소스별로 유지하며, 그 전에 해당 소스를 다시 요청하지 않는다. 네트워크·인증·접근 오류는 기존 GitHub 오류 처리와 같은 원칙으로 안내한다.
- 전체 빈 결과와 현재 로딩된 항목에서의 필터 불일치를 구분한다. 다음 페이지가 있으면 현재 목록만 검색했다는 점과 추가 조회 가능성을 표시한다.
- 공개 목록 없음, 조회 가능한 항목 없음, Owner 조회 오류, 인증 조회 오류를 구분한다. 오류로 아직 읽지 못한 Private 저장소의 존재나 정보를 추정하지 않는다.

불필요한 토스트는 추가하지 않는다. 로딩에는 기존 인디케이터를 활용한다. Owner 목록의 실제 HTTP 요청도 공통 요청 수에 포함하며, 대기열은 진행 요청 수에서 제외한다. `/users`·`/user` 목록 요청을 특정 저장소의 요청으로 분류하지 않으므로 Split view 열별 요청 집계를 오염시키지 않는다.

## 메모리 캐시와 수명

`OwnerRepositories`가 두 입력 UI의 조회 상태를 공유하고 기존 `GitHubReader`의 요청·취소·집계 경로를 재사용한다. 성공한 소스의 페이지 결과는 첫 페이지 완료 시점부터 메모리에서 60초 동안 재사용하고, 최근 사용한 최대 10개 Owner를 보관한다. 추가 페이지 로딩은 캐시 만료 시각을 연장하지 않는다. 같은 이름의 대소문자 차이는 같은 캐시 대상으로 처리한다. 영구 Owner 기록·새 localStorage 키·Service Worker API 캐시는 만들지 않는다.

- 유효한 캐시로 다시 열면 이미 로딩한 결과와 페이지 상태를 재사용한다. 캐시가 없거나 만료됐으면 다음 명시적 제출에서 정상 조회한다.
- PAT 추가·변경·삭제 시 표시 중인 목록과 캐시를 무효화한다. 이전 PAT로 받은 Private 이름이 새 인증 컨텍스트에 남지 않는다.
- 다른 탭에서 PAT 저장이 변경되면 Owner 목록을 닫고 인증 조회 컨텍스트를 비운다. 이 탭에서 PAT를 명시적으로 다시 적용할 때까지 Owner 인증 목록은 조회하지 않는다. 기존 그래프의 인증 동작은 바꾸지 않는다.
- 목록 닫기·다른 Owner 제출·입력 컨텍스트 종료는 진행 중 요청을 취소하고, 취소를 무시한 늦은 응답도 현재 목록에 반영하지 않는다. 닫기 전에 완료된 유효한 캐시는 재사용할 수 있다.

## 접근성과 반응형

일반 화면과 Split view의 목록 검색창은 같은 글자 크기를 사용한다. 화면 너비가 800px 이하이면 입력 글자는 16px로 유지하고 placeholder만 14px로 낮춘다. 더 넓은 화면에서는 기존 13px를 유지한다.

**Load more** 버튼은 접근성 이름 **Load more repositories**를 제공하고 Tab 순서에 포함한다.
비활성 상태는 `aria-disabled`로 전달하고 포커스는 허용하되 클릭·Enter·Space로 요청하지 않는다.
일반 화면 필터 입력에서 마지막 선택 가능 항목까지 ↓로 이동한 뒤 ↓를 한 번 더 누르면 버튼에 포커스를 둔다.
Split view에서는 마지막 선택 가능 체크박스에서 ↓로 버튼에 포커스를 둔다.
선택 가능 항목이 없으면 필터 입력에서 ↓로 버튼에 접근한다.
버튼이 표시되지 않으면 마지막 선택 가능 항목에서 ↓를 눌렀을 때 첫 항목으로 순환한다.

버튼에서 Enter·Space로 다음 페이지와 재시도 가능한 실패 페이지를 요청한다.
완료되면 일반 화면은 필터 입력으로 포커스를 되돌리고 새로 추가된 첫 선택 가능 항목을 활성화하며,
Split view는 해당 항목의 체크박스에 포커스를 둔다.
새 선택 가능 항목이 없으면 사용 가능한 버튼에 포커스를 두고, 버튼이 없거나 비활성 상태이면 필터 입력으로 돌아간다.

검색 입력과 목록에 접근성 이름을 제공하고, 현재 키보드 항목·선택·로딩 상태를 전달한다. 일반 화면에서는 필터 입력의 ↑/↓로 항목을 이동하고 Enter로 바로 연다. Split view에서는 필터 입력의 ↑/↓로 네이티브 체크박스에 포커스를 옮기고, 체크박스의 ↑/↓로 선택 가능한 행을 이동하며 Enter·Space로 체크를 전환한다. Tab으로 **Add N repositories** 버튼에 이동해 일괄 추가를 확정한다. Escape는 Owner 목록만 닫고 Split view 설정 창을 유지한다. 목록 내부 키보드 조작이 상위 폼을 다시 제출하지 않게 처리하며, 목록 종료 후 기존 입력으로 돌아가서 편집할 수 있다.

기존 테마 색상과 컨트롤 스타일을 사용한다. 일반 화면의 드롭다운은 연결된 저장소 입력 필드의 좌우 경계와 너비를 따르며, 별도 고정 너비로 확장하지 않는다. 입력 필드 크기가 바뀌면 목록도 따라 바뀌고, 보이는 뷰포트가 더 좁으면 화면 안쪽 여백을 유지하도록 제한한다. Split view의 인라인 목록은 기존 설정 본문 너비와 포커스 외곽선 여백을 따른다. 좁은 화면에서는 사용 가능한 뷰포트 높이와 스크롤 영역 안에 목록을 제한하고, 긴 이름·설명 때문에 가로로 넘치지 않도록 한다. Split view 설정에서는 기존 고정 하단 액션과 중간 스크롤 영역을 유지한다. 추가 모달·애니메이션·기기별 입력 정책은 만들지 않는다.

## 구현과 검증 기준

- `src/repository/repoInput.ts`는 Owner 입력을 판별하고 입력 필드를 정규화한다.
- `src/repository/OwnerRepositories.ts`는 공개·인증 조회와 페이지·오류·메모리 캐시·인증 수명을 관리한다.
- `src/repository/OwnerRepositoryPicker.tsx`는 공통 필터·목록·선택·로딩·오류·추가 페이지 UI를 제공한다.
- `src/repository/useOwnerRepositoryPicker.ts`는 두 입력에 명시적 제출과 목록 닫기·입력 컨텍스트 처리를 연결한다.
- `src/repository/RepositoryInput.tsx`와 `src/monitor/MonitorSetup.tsx`는 직접 입력·최근 항목에서 저장소를 열거나 추가한다.
- `src/main.tsx`는 앱 수명의 조회 모델을 PAT 변경 경로에 연결한다.

회귀 검증에서는 Owner·직접 주소·URL·잘못된 입력의 분기, 익명·제한 PAT·잘못된 PAT,
중복 제거·정렬·Owner 필터·독립 페이지 처리·오류 보존·재시도를 확인한다.
취소·늦은 응답·캐시 재사용·PAT 변경 시 비공개 항목 제거를 검증한다.
최초 조회·추가 페이지·재시도마다 시작한 요청이 모두 종료되기 전에는 부분 목록을 반영하지 않는지도 확인한다.

일반 화면의 즉시 단일 선택과 Split view의 체크·명시적 일괄 추가를 확인한다.
체크 순서, 필터·페이지 변경 시 유지, 목록 닫기·Owner·PAT 변경 시 초기화도 확인한다.
키보드·터치·외부 닫기, 필터의 로컬 검색과 추가 조회 차단, 하단 사용자 스크롤 로딩,
체크 시 요청이 발생하지 않는지, 중복 방지와 기존 항목·추가 예정 항목을 합친 32개 제한, 기존 요청 집계를 검증한다.

브라우저의 합성 응답으로 확인한 동작, 실제 GitHub의 응답·인증 범위, 실기기의 입력·접근성 검증은 구분해 보고한다.

## 범위에서 제외

입력 중 원격 자동완성, Owner 즐겨찾기·영구 검색 이력, 일반 화면의 저장소 다중 선택, Star·언어 기반 추천, GraphQL, 새 서버·데이터베이스·의존성·인증 화면은 추가하지 않는다. 기존 DAG·브랜치·갱신·PWA 정책은 유지한다.
