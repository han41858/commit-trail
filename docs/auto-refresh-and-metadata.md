# Commit Trail — 자동 갱신 및 커밋 메타데이터 확장 명세서

## 1. 개요

Commit Trail은 GitHub 저장소의 변경을 감지해 세로형 Git DAG에 반영한다.
Git 태그·GitHub Release·GitHub Actions 실행을 커밋에 연결해, 커밋과 브랜치의 변화뿐 아니라 자동화 작업의 진행 상황도 보여준다.

별도 백엔드·WebSocket·Webhook 없이 GitHub REST API를 읽기 전용으로 폴링한다.
필요한 범위만 조회하며 그래프 위치와 사용자 탐색 상태를 보존한다.
메타데이터 변경은 DAG 구조를 바꾸지 않는다.

## 2. 자동 갱신 설정

### 2.1 UI

일반 화면의 `Options`에서 `Auto refresh`와 `Interval`을 설정하고 툴바에서 수동 새로고침을 실행한다.
진행·성공·오류 상태는 마지막 갱신 시도 완료 시각과 구분해 표시한다.

#### 수동 갱신 버튼의 주기 표시

- 수동 갱신 버튼의 배경은 12시부터 시계방향으로 채워진다. Split view에서 도구를 접으면
  책갈피 `>` 탭을 아래에서 위로 채우고, 펼치면 버튼의 원형 채움을 표시한다.
  두 표시는 같은 `RefreshLoop.nextAt`과 선택한 주기를 따르며, 접거나 펼쳐도 기한을 다시 시작하지 않는다.
- 자동 갱신 OFF·초기 로딩·Rate Limit 대기 중에는 채움을 숨긴다.
  일반 화면은 갱신 실행 중에도 채움을 숨긴다. Split view는 열별 작업 진행 표시와 공통 예정 시각의 채움을 구분한다.
- DOM에 반영한 뒤 실제 예정 시각에 애니메이션을 맞추고, 탭·네트워크 복귀 시 다시 맞춘다.
  작은 SVG의 CSS 애니메이션만 사용하므로 별도 폴링·API 요청이나 주기적 Canvas 렌더링이 없다.
- 두 테마 모두 툴바와 같은 surface 배경에 테마의 파란 강조색을 40% 불투명도로 채운다.
  Hover 중에도 아이콘은 기본 텍스트 색상을 유지하며, Hover 테두리와 포커스 표시는 기존 강조색을 사용한다.
  채움에만 불투명도를 적용하고 동작 줄이기 설정에서는 채움 전체를 숨긴다.
- 채움은 보조 표시다. 버튼 아이콘·접근성 이름·비활성화 상태로 기능과 조작 가능 여부를 알리고,
  성공·실패는 상태 문구로 알린다. 채움을 숨겨도 수동 갱신 정책은 바뀌지 않는다.

### 2.2 갱신 주기

| 구분            | 기본 주기 |
| --------------- | --------- |
| PAT 인증 사용자 | 1분       |
| 비인증 사용자   | 5분       |
| 수동 새로고침   | 즉시      |

자동 갱신은 기본으로 켜며 사용자가 끌 수 있다. 주기는 30초·1분·5분 중 선택하며, 30초는 PAT를 적용한 경우에만 제공한다.

테마·자동 갱신 ON/OFF·갱신 주기는 localStorage의 `commit-trail.view-options`에 저장해 새로고침과 재실행 뒤에도 유지한다.
주기를 직접 고르지 않으면 `interval`은 `null`이며 인증 상태별 기본 주기를 따른다.
저장된 주기가 30초여도 PAT가 없으면 5분으로 동작한다. 알 수 없는 값은 항목별 기본값으로 되돌리고, 다른 탭의 설정 변경은 다음 로딩 때 반영한다.

커밋·브랜치·태그·릴리즈·Actions에 같은 주기를 적용한다. 실제 요청은 [데이터별 조회·캐시 정책](#9-공통-자동-갱신)에 따른다.

### 2.3 실행 조건

| 상황              | 동작                                       |
| ----------------- | ------------------------------------------ |
| 활성 탭           | 지정한 주기로 갱신                         |
| 백그라운드 탭     | 자동 갱신 일시 중지                        |
| 탭 복귀           | 마지막 갱신 이후 설정 주기가 지났다면 갱신 |
| 네트워크 오프라인 | 갱신 중지                                  |
| 네트워크 복구     | 갱신 재개                                  |
| 저장소 변경       | 이전 요청 취소 후 새 저장소 조회           |
| 자동 갱신 OFF     | 주기적 요청 중지                           |
| 수동 새로고침     | 현재 저장소 즉시 갱신                      |

일반 화면과 Split view는 정규 스케줄을 소유하는 `RefreshLoop` 한 개를 공유한다.
탭이나 네트워크가 복귀했을 때 기한을 넘겼으면 한 번 갱신한다.
자동 실행 콜백은 현재 예정 시각·자동 갱신 설정·초기 로딩 상태를 다시 확인한다.
같은 저장소의 진행 중 갱신은 중복 실행하지 않는다.

Split view 첫 진입에서는 이력과 메타데이터 초기 작업이 모두 종료될 때까지 자동 갱신을 예약하지 않고 수동 새로고침을 비활성화한다.
`MonitorSession.settled`는 기본·추가 저장소의 이력, 예약된 경계 요청과 늦게 시작한 메타데이터 작업을 관찰한다.
오류도 종료로 처리하며, 성공·실패와 관계없이 초기 작업이 끝난 시점부터 설정한 전체 주기를 적용한다.
기본 저장소의 이력 오류도 이후 수동·자동 갱신에서 `History.retry()`로 재시도하므로 브라우저를 새로고침하지 않고 복구할 수 있다.

자동·수동 갱신 모두 일반 화면은 작업 종료 후, Split view는 공통 dispatch가 반환된 뒤 다음 예정 시각을 계산한다.
오래 걸리는 열의 완료는 다음 dispatch를 막지 않으며, Rate Limit 대기는 별도로 적용한다.

### 2.4 갱신 완료 시각

`RefreshLoop.lastCompletedAt`은 마지막 성공 시각이 아니라 갱신 시도가 끝난 시각이다.
일반 화면은 이력과 메타데이터가 모두 끝난 뒤 기록한다. API·네트워크·Rate Limit 오류나 예외도 실제 종료 시각을 기록하되 오류·재시도 상태는 별도로 유지한다.
Rate Limit 대기로 시작하지 못한 작업은 완료로 기록하지 않는다.

Split view는 해당 주기에 새로 시작한 저장소 작업이 모두 끝난 시각을 기록한다.
열별 결과는 독립적으로 반영하고, 일부 또는 전체 실패도 완료로 기록한다.
이전 주기부터 진행 중이어서 건너뛴 작업은 이번 주기의 대기에 포함하지 않는다.
새로 시작한 작업이 없거나 그 작업의 대상이 모두 제거되면 완료 시각을 변경하지 않는다.
완료 추적에 별도 타이머나 API 요청을 사용하지 않는다.

초기 작업이나 갱신 시도가 남아 있으면 초기 완료 시각을 먼저 기록하지 않는다.
모드·저장소·인증 범위가 교체되거나 세션이 종료되면 이전 범위의 늦은 완료를 무시한다.
활성 Split view에서 구성을 편집할 때는 [유지되는 열의 작업을 보존하는 규칙](monitor-mode.md#활성-split-view-구성-변경)을 따른다.

## 3. 커밋·브랜치 자동 갱신

### 3.1 브랜치 변경 감지

GitHub Branches API에서 받은 현재 브랜치 목록과 HEAD SHA를 이전 결과와 비교한다.

| 변경 유형        | 처리                         |
| ---------------- | ---------------------------- |
| 변경 없음        | 기존 그래프 유지             |
| 브랜치 생성      | 새로운 브랜치 참조 추가      |
| 브랜치 삭제      | 기존 브랜치 참조 제거        |
| HEAD SHA 변경    | 해당 브랜치의 커밋 이력 갱신 |
| 기본 브랜치 변경 | 기본 브랜치 표시 갱신        |

브랜치 목록은 한 갱신 주기에 최대 3페이지씩 이어서 확인한다.
일부 페이지만 받은 상태에서는 삭제를 확정하지 않는다. 목록 조회에 실패하면 기존 상태를 유지하고 이후 갱신에서 재시도한다.

스크롤 경계·브랜치 탐색·브랜치 선택 목록의 추가 조회는 브랜치 갱신을 막지 않는다.
늦게 도착한 응답은 갱신 버전과 대조한다. 최초 로딩·기준 브랜치 변경·방향 변경으로 탐색을 다시 시작하는 동안에는 해당 저장소의 갱신을 건너뛴다.

GitHub에서 병합 직후 브랜치가 삭제되기까지 1~4초 늦게 반영될 수 있다.
이 사이에 새 커밋과 곧 사라질 브랜치가 함께 표시될 수 있으므로, 이미 알던 브랜치의 HEAD가 바뀌면 해당 저장소의 브랜치를 7초 후 한 번 더 확인한다.

- squash·rebase·merge commit을 구분하지 않고, 병합이 아닌 push로 HEAD가 바뀐 경우에도 적용한다.
  자동·수동 갱신 뒤에만 예약하며 재확인 결과로 다시 예약하지 않는다.
  Split view에서도 바뀐 저장소별로 HEAD 변경을 확인한 시점부터 7초를 기다린다.
- 저장소 정보와 브랜치 목록만 읽으며 같은 갱신의 태그·릴리즈·Actions가 끝나기를 기다리지 않는다.
  진행 표시·완료 시각·다음 갱신 시각을 바꾸지 않고, 비인증 자동 갱신의 두 번째 전체 조회로 세지 않는다.
- 대기 중 새 정규 갱신이 그 저장소를 다시 읽기 시작하면 재확인 대상에서 뺀다.
  저장소·모드가 바뀌거나 Rate Limit 대기 중이면 대상을 버린다. 탭이 숨겨져 있으면 다시 보일 때 실행한다.

브랜치 목록·이름 조회는 `cache: 'no-cache'`로 브라우저 HTTP 캐시를 재검증한다.
GitHub 응답을 60초 동안 그대로 재사용하면 삭제된 브랜치를 살아 있는 것으로 읽을 수 있다.
앱이 ETag를 보내는 조건부 요청은 브라우저 캐시를 거치지 않는다.

### 3.2 커밋 증분 조회

HEAD SHA가 바뀌면 새 HEAD부터 기존에 아는 커밋까지 필요한 이력을 읽는다.
기존 데이터를 재사용하고 여러 브랜치에서 같은 커밋을 발견해도 SHA당 하나만 추가한다.
실제 부모 SHA 관계를 반영해 필요한 그래프 영역을 다시 계산하며, 전체 저장소 이력을 다시 다운로드하지 않는다.

고정 SHA 첫 페이지의 검증·캐시와 날짜 필터·오래된 순 후속 페이지의 예외는 [공통 API 및 로딩 규칙](specification.md#52-api-및-로딩)을 따른다.
갱신 중 빈 응답이나 요청한 HEAD가 없는 첫 페이지를 받으면 기존 커밋·브랜치 참조·HEAD를 유지하고 오류를 표시한다.
잘못된 응답은 캐시하지 않으므로 다음 갱신에서 같은 HEAD를 다시 조회한다.

### 3.3 Force Push 및 Rebase

Force Push·Rebase·Reset 등으로 이력이 바뀌면 새 HEAD에서 접근할 수 있는 이력과 기존 커밋의 공통 조상을 확인한다.
해당 브랜치의 참조·경로를 갱신하고, 더 이상 그 브랜치에서 접근할 수 없는 커밋의 연결을 다시 판정한다.
다른 브랜치에서 접근할 수 있는 커밋은 유지하며, 부분 조회로 확정하지 못한 관계는 미완료 경계로 표시한다.

완전한 브랜치 목록으로 삭제를 확인하면 삭제된 참조에서만 이어지는 로딩된 경로를 정리한다.
다른 카탈로그 HEAD가 미조회 상태여도 정리를 계속 유예하지 않는다.
현재 참조에서 실제 부모로 연결되는 커밋과 살아 있는 참조의 직전 HEAD 이력을 보호하므로 공유 조상·실제 Merge Commit의 분기·새 HEAD 아래 미완료 경계는 유지한다.
Squash Merge 후 살아 있는 참조가 가리키지 않는 분기는 정리하되 유효한 SHA 페이지 캐시는 남긴다.
선택한 기준 브랜치 자체가 삭제된 경우에는 기존 캐시 이력과 삭제 안내를 유지한다.

완전한 목록을 반영한 갱신보다 먼저 시작한 활동 탐색·추천·이름 조회·브랜치 페이지의 응답은 최신 참조 상태와 대조한다.
삭제되거나 HEAD가 바뀐 참조의 오래된 응답으로 이름이나 이력을 되살리지 않으며, 완전한 목록 수신 후에는 이전 목록의 추가 페이지 탐색을 종료한다.
사라진 부모 경계의 늦은 결과와 오류는 [공통 로딩 규칙](specification.md#52-api-및-로딩)을 따른다. 인증 실패와 Rate Limit 오류는 계속 보고한다.

### 3.4 부분 데이터 처리

전체 이력이 메모리에 없을 때는 존재하지 않는 커밋과 아직 조회하지 않은 부모를 구분해 연결 경계를 표시한다.
미조회 부모의 판정·삭제 후 경계 복원·고정 SHA 페이지 재사용·레인 안정성은 [공통 API 및 로딩 규칙](specification.md#52-api-및-로딩)을 따른다.
부분 이력의 유효한 캐시는 유지하되 `Partial history` 상태 문구와 일반 갱신 시각의 부분 이력 안내 툴팁은 표시하지 않는다.

## 4. 자동 갱신 시 스크롤 동작

### 4.1 최신 커밋을 보고 있는 경우

최신 → 과거 방향에서는 새 커밋이 그래프 상단에 나타나고 기존 커밋이 아래로 밀린다.
과거 → 최신 방향에서는 새 커밋이 하단에 나타난다. 갱신 전에 최신 이력을 보고 있었다면 새 최신 위치를 따라간다.
최신순 상단에서는 기준 브랜치 최초 조회 뒤 다른 브랜치에서 비동기로 도착한 더 최신 커밋도 따라간다.
오래된 이력 추가나 변경 없는 갱신으로 최신 위치로 이동하지 않는다.

최신 위치까지 약 240ms 동안 부드럽게 스크롤한다. 이동 중 새 결과가 도착하면 추적을 이어가고,
휠·터치·포인터·스크롤 키 입력으로 사용자가 개입하면 중단한다.
숨긴 탭과 동작 줄이기 설정에서는 애니메이션 없이 즉시 이동한다.

### 4.2 과거 이력을 탐색하는 경우

새 커밋이 추가되어도 최신 위치로 강제 이동하지 않는다.
`scrollPosition`은 기존 위치의 커밋 SHA로 오프셋을 보정한다. 그 SHA가 사라지면 가장 가까운 남은 커밋을 기준으로 삼는다.
유효한 커밋 선택과 경로 강조는 유지한다.

### 4.3 최신 위치 판단

데이터 갱신 **전**의 뷰포트와 스크롤 좌표를 사용한다.
최신순은 상단, 오래된 순은 하단에서 커밋 두 행 높이(`ROW * 2`) 이내를 최신 위치로 판단한다.
갱신 후 좌표로 최신 여부를 다시 판단하지 않는다.

### 4.4 공통 정책

변경이 없거나 메타데이터만 바뀌면 스크롤을 움직이거나 그래프를 초기화하지 않는다.
추가 이력 조회는 [공통 API 및 로딩 규칙](specification.md#52-api-및-로딩)을 따른다.
최신 추적 중 지나가는 임시 화면에서는 이력 요청을 시작하지 않으며, 가시 커밋의 Actions Job 조회도 실제 표시 범위를 기준으로 한다.
Split view는 이 규칙을 열마다 독립적으로 적용한다.

## 5. Git 태그 표시

### 5.1 UI

커밋당 버전 아이콘은 하나만 표시한다. Release가 하나 이상 있으면 🚀, Release 없이 태그만 있으면 🏷️를 표시한다. 둘 다 없으면 표시하지 않는다.
일반·분할 화면과 좁은·넓은 화면, 자동 갱신으로 도착한 데이터에 같은 규칙을 적용한다.
아이콘은 원형 노드 왼쪽에 별도로 표시하며 숨긴 태그 아이콘의 빈 간격은 남기지 않는다.

Hover는 태그 또는 Release 이름을 툴팁으로 표시하고, 클릭·탭은 연결된 태그와 Release를 모두 볼 수 있는 커밋 상세를 연다.
태그 이름을 선택하면 GitHub 원본 페이지로 이동한다. 태그·릴리즈 이름은 각 아이콘과 같은 줄에 표시하고, Release 이름과 연결 태그 이름이 같으면 반복하지 않는다.
상세의 작성자 `by 이름` 표기는 [공통 상세 UI](specification.md#3-ui-원칙)를 따른다.
아이콘 우선순위는 표시 규칙이며 연결 태그나 링크·조회·캐시에는 영향을 주지 않는다.

### 5.2 데이터 처리

GitHub REST API에서 태그 목록을 페이지 단위로 읽고 중복을 제거한다.
Lightweight Tag와 Annotated Tag를 모두 지원하며, Annotated Tag는 최종 대상 커밋 SHA를 확인해 연결한다.
일부 조회 범위에 태그가 없다는 이유로 해당 커밋에 태그가 없다고 확정하지 않는다.

## 6. GitHub Release 표시

### 6.1 UI

그래프 아이콘과 상세 열기는 [버전 아이콘 공통 규칙](#51-ui)을 따른다.
상세에는 연결된 Release를 모두 나열하고 이름·버전·게시 시각·GitHub 링크를 표시한다. Pre-release 여부를 구분한다.

### 6.2 데이터 처리

GitHub Releases API를 페이지 단위로 읽고 접근 가능한 Draft Release도 처리한다.
Release는 연결 태그가 가리키는 최종 커밋 SHA에 연결한다.

### 6.3 의미 구분

🚀 아이콘은 **GitHub Release가 존재한다는 뜻**이다. 실제 운영 환경에 배포됐다는 뜻이 아니며 GitHub Deployments API로 배포 상태를 추적하지 않는다.

## 7. GitHub Actions 상태 표시

### 7.1 기본 표현

Actions 실행 정보가 있는 커밋은 원형 노드 주위에 도넛형 상태 링을 표시한다.

| 상태                                                   | 표현             |
| ------------------------------------------------------ | ---------------- |
| Actions 정보 없음                                      | 기존 원형 점     |
| 대기 중                                                | 회색 링          |
| 실행 중                                                | 노란색 진행률 링 |
| 모두 종료되고, 하나 이상 성공하며 나머지는 성공·건너뜀 | 초록색 완료 링   |
| 실패·시간 초과·시작 실패                               | 빨간색 완료 링   |
| 모두 취소                                              | 회색 완료 링     |
| 건너뜀만 존재·중립·취소 혼합·실행되지 않음·결과 미확정 | 회색 링          |

링은 커밋 중심점·크기·레인 간격이나 경로 색상 판정을 바꾸지 않는다. 선택 시 링을 확대하고 노드를 강조한다.
회색 링의 기본 불투명도는 일반·분할 화면과 두 테마에서 40%다. 이 값은 성공·실패 링, 실행 중 진행률, 툴팁·상세의 상태 아이콘에는 적용하지 않는다.
경로 색상과 강조 배율은 [공통 경로 명세](dag-hover-highlight.md)를 따른다.

### 7.2 여러 워크플로 합산

한 커밋의 여러 워크플로에 속한 Job을 합산한다. 전체 작업 시간이 아니라 **완료된 Job 개수**를 기준으로 한다.

**진행률 = 완료된 Job 수 / 전체 Job 수 × 100**

예시:

| 워크플로 | 전체 Job | 완료 Job |
| -------- | -------: | -------: |
| Build    |        3 |        3 |
| Test     |        4 |        2 |
| Deploy   |        3 |        0 |
| 합계     |       10 |        5 |

이 경우 커밋 노드에 50%를 표시한다.

### 7.3 진행률 계산 규칙

- 최신 실행 시도의 Job을 ID로 중복 제거한다. 성공·실패·취소·건너뜀 등 `completed`인 Job만 완료 개수에 포함한다.
- Job 목록과 분모가 확정되면 실제 비율을 표시한다. Matrix Job 등으로 분모가 바뀔 수 있으며, 미확정 상태에서는 퍼센트 없이 회전하는 도넛을 표시한다.
- 진행률을 임의로 올리지 않는다. 모든 Job이 종료되어 완료율이 100%여도 GitHub가 최종 실행 결과를 확정하기 전에는 성공으로 표시하지 않는다.

### 7.4 최종 상태

GitHub API의 `status`와 `conclusion`을 구분해 아래 순서로 대표 상태를 결정한다.
모든 워크플로가 끝나면 진행률 대신 최종 상태를 표시한다.

1. 실행 중인 워크플로가 하나라도 있으면 실행 중, 실행 중인 작업 없이 대기 중인 워크플로가 있으면 대기로 표시한다.
2. 진행·대기 중인 실행이 없고 완료된 실행 중 `failure`·`timed_out`·`startup_failure`가 하나라도 있으면 실패로 표시한다.
3. 모두 `completed`이고 `success`가 최소 하나 있으며 나머지가 모두 `success` 또는 `skipped`이면 성공으로 표시한다.
4. 모두 `completed`이며 결과가 모두 `cancelled`이면 취소로 표시한다.
5. 그 밖의 조합은 `skipped` 집계 상태로 표시한다. 전체 건너뜀, 중립·취소·조치 필요·오래된 상태가 섞인 결과, 미확정·알 수 없는 결과가 포함된다.

모든 저장소와 일반·분할 화면에서 워크플로 이름과 무관하게 같은 규칙을 적용한다.
보라색 기타 결과 링을 사용하지 않으며, 알 수 없는 결과가 섞여도 확인된 실패는 숨기지 않는다.
대표 상태는 그래프의 집계일 뿐이므로 상세에서는 각 실행의 원본 `conclusion`과 상태 아이콘을 구분한다.

### 7.5 재실행

Workflow Run은 `run_id`로 식별하며, 동일 실행의 여러 시도 중 최신 `run_attempt`의 상태와 Job만 집계한다.
완료된 실행도 재실행되면 다시 진행 중으로 표시할 수 있다.
최근 실행 목록 밖으로 밀려난 진행 중 실행도 최종 상태까지 확인한다.
확정된 완료 Job 캐시는 재사용하고, 최근 목록에서 새 실행이나 `run_attempt` 변경을 발견하면 다시 추적한다.

### 7.6 Actions 상세 정보

일반·분할 화면 모두 커밋 상세에 연결된 워크플로를 표시한다. 그래프 Hover는 경로 강조와 이미 조회한 툴팁만 표시하며 선택을 바꾸거나 상세 조회를 시작하지 않는다.

- 상태 아이콘 → 워크플로 이름 → 진행 중 Job 개수 → 경과 시간·`Attempt` 순으로 한 줄에 표시한다.
  이름은 GitHub Actions 실행 링크이며, 긴 이름은 말줄임하고 전체 이름은 툴팁으로 제공한다.
- 상태 아이콘은 배경 없는 16px SVG로 표시하고 텍스트와 세로 중앙에 맞춘다.
  성공은 초록 체크, 진행 중은 노란 회전 링, 대기는 회색 시계, 실패·시간 초과는 빨간색으로 표시한다.
  취소·건너뜀·조치 필요·알 수 없음도 모양으로 구분하고, 동작 줄이기 설정에서는 회전을 멈춘다.
  완료 상태를 별도 텍스트로 반복하지 않는다.
- 진행 중 실행은 이름 뒤에 완료 Job 수 / 전체 Job 수를 표시한다. 미확정이면 `?/?`를 표시하고 완료된 실행은 개수를 생략한다.
  경과 시간·`Attempt`는 작은 보조 색상 글자로 오른쪽 정렬하며 줄바꿈하거나 생략하지 않는다. `Elapsed` 표제는 툴팁으로 제공한다.
- 실행별 경과 시간은 `run_started_at`부터 계산한다. 완료된 실행은 마지막 상태 갱신 시각 `updated_at`에 고정하고, 시각이 누락되거나 잘못됐으면 `—`로 표시한다.
  진행 중인 상세 화면의 시간만 로컬에서 갱신하며 추가 API 요청을 보내지 않는다.
- Actions 제목 옆의 노란색 `완료/전체 jobs (정수%)`는 합계가 확정된 진행·대기 상태에만 표시한다.
  별도의 In progress 줄·진행바·반복 설명은 표시하지 않는다.
- 제목 옆 시계 아이콘의 전체 경과 시간은 최신 시도 중 가장 이른 시작부터 계산한다.
  모든 실행이 끝나면 가장 늦은 최종 상태 갱신 시각으로 고정한다. 병렬 실행을 중복 합산하거나 불명확한 시각을 추측하지 않는다.

상세와 그래프는 같은 커밋 선택을 사용한다. 상세를 닫거나 다른 커밋을 고르면 이전 선택의 조회 대상을 해제한다.
진행 중이던 조회 결과는 캐시에 보관할 수 있으나 닫힌 상세를 다시 열지 않는다.
Split view의 [공용 상세와 열별 선택](monitor-mode.md#그래프와-상세), 선택·고정 강조의 [공통 입력 수명](dag-hover-highlight.md#입력과-수명)을 따른다.

## 8. Actions 데이터 조회

### 8.1 최근 Workflow Runs 일괄 조회

커밋마다 요청하는 대신 저장소의 최근 Workflow Runs를 일괄 조회하고 필요한 페이지를 이어 읽는다.
`head_sha`로 연결하고 `run_id`별 최신 시도와 필요한 Job으로 대표 상태·진행률을 계산한다.
최근 실행과 가시 커밋을 우선하며 전체 Actions 이력을 다운로드하지 않는다.

Job 조회 대상은 선택한 커밋과 화면에 보이는 최대 24개 커밋이다. 한 실행의 Job은 최대 5페이지씩 이어서 확인한다.
같은 커밋에 진행 중인 실행이 있으면 합산 분모에 필요한 완료 실행의 Job도 채운다.
완료 실행에 Job 페이지가 남아 있으면 이어 읽어 스냅샷을 완성하고, 확정된 캐시는 반복 조회하지 않는다.
전체 실행이 종료된 커밋은 Job을 더 읽지 않고 최종 상태를 유지한다. 실패나 미완료 페이지를 임의의 진행률로 바꾸지 않는다.

### 8.2 과거 커밋

최근 조회 결과에 없는 커밋은 기본 원형 노드로 표시하되 Actions가 없다고 확정하지 않는다.
과거 커밋을 선택하면 필요한 경우 `head_sha`로 실행을 조회해 메모리에 캐시한다.
GitHub의 보존 정책에 따라 오래된 실행은 확인하지 못할 수 있다.

선택한 SHA의 실행은 최대 3페이지씩 읽고 상세 스크롤로 이어간다. 추가 페이지를 읽을 때 이미 받은 첫 페이지나 무관한 저장소 전체 이력을 다시 훑지 않는다.
완료한 목록은 재사용하되, 정규 갱신에서 선택한 커밋의 진행 중 실행은 다시 확인한다. 진행 중인 실행의 미완료 Job 페이지도 이어 읽는다.

### 8.3 커밋 연결 정확성

GitHub가 반환한 실제 `head_sha`가 그래프의 커밋 SHA와 일치할 때만 연결한다.
PR 임시 병합 SHA처럼 불일치하는 실행은 추측으로 다른 커밋에 연결하지 않는다.
하나의 SHA에 연결된 여러 실행은 모두 집계에 반영한다. 외부 CI 서비스와 GitHub Checks API는 연동하지 않는다.

## 9. 공통 자동 갱신

공통 주기에 데이터별 변경을 확인한다. 모든 API를 매번 호출하지는 않는다.

### 9.1 데이터별 갱신

| 데이터  | 처리                                    |
| ------- | --------------------------------------- |
| 브랜치  | HEAD SHA 및 목록 변화 확인              |
| 커밋    | 변경된 브랜치의 이력 증분 조회          |
| 태그    | 새 태그 및 변경된 참조 확인             |
| 릴리즈  | 새 릴리즈 및 변경된 정보 확인           |
| Actions | 최근 Workflow Runs 및 진행 중 상태 확인 |

Actions 상태와 태그·릴리즈는 커밋 SHA가 그대로여도 바뀔 수 있으므로 커밋 변경과 별도로 확인한다.
비인증 자동 갱신은 아래의 조회 절약 정책을 따른다.

### 9.2 변경된 정보만 반영

커밋 구조가 바뀔 때만 필요한 DAG 레이아웃을 다시 계산한다.
태그·릴리즈만 바뀌면 버전 아이콘을, Actions 상태만 바뀌면 해당 커밋 노드의 표시를 갱신한다.
변경이 없으면 그래프를 유지하며 화면 전체를 재구성하거나 불필요하게 스크롤을 이동시키지 않는다.

### 9.3 API 호출 효율화

가능한 경우 ETag와 `If-None-Match`를 사용하고 중복 요청을 공유한다.
최초 로딩의 저장소 정보와 첫 브랜치 페이지, 메타데이터의 태그와 Actions는 병렬로 요청한다.
릴리즈는 태그 결과가 필요하므로 태그 뒤에 조회한다.

태그·릴리즈·최근 실행 목록은 페이지당 최대 100개다. 태그·릴리즈는 이미 읽은 목록 페이지를 조건부로 재확인한다.
추가 페이지는 커밋 상세 하단의 스크롤로 요청한다. 짧은 팝업은 처음 한 배치만 자동으로 채우고,
이후 휠·터치·키보드로 아래 방향 탐색을 계속할 때 이어 읽는다.

커밋 객체·유효한 고정 SHA 페이지·변경 없는 상세와 Annotated Tag 객체를 재사용한다.
Actions Job 캐시 규칙은 [Actions 데이터 조회](#8-actions-데이터-조회)를 따른다.
캐시는 현재 저장소·토큰 세션의 메모리에만 유지하며 API 데이터는 영속 저장하지 않는다.

Rate Limit 헤더와 기본·보조 요청 제한을 확인한다. 한도에 도달하면 자동 갱신을 멈추고 해제 시각 또는 재시도 가능 시각을 기준으로 재개한다.
오류 상황에서 제한을 무시하고 반복 요청하지 않는다.

### 9.4 비인증 자동 갱신

GitHub는 비인증 304 응답도 시간당 60회 한도에서 차감한다.
일반 화면과 Split view의 비인증 **자동** 갱신은 저장소별로 먼저 `GET /repos/{owner}/{repo}`를 조회한다.
`pushed_at`이 바뀌면 브랜치·태그·릴리즈·Actions를 확인하고, 바뀌지 않으면 아래 예외 외에는 저장소 정보 한 건으로 끝낸다.

- 최초 로딩 뒤 첫 자동 갱신은 전체 조회다. push보다 브랜치·Actions 응답이 늦게 반영될 수 있으므로,
  새 push를 확인한 뒤 같은 `pushed_at`으로 전체 조회를 한 번 더 마친 뒤부터 조회를 줄인다.
- 진행 중인 Actions가 있으면 종료까지 Actions를 함께 조회한다.
- 직전 태그·릴리즈·Actions 조회가 실패했으면 push가 없어도 해당 데이터를 성공할 때까지 다음 주기에 재시도한다.
- 저장소 정보 조회에서 Rate Limit을 확인하면 그 주기의 후속 조회를 시작하지 않는다.

수동 갱신과 PAT를 적용한 갱신은 이 조회 절약 정책을 사용하지 않는다.
push 없이 바뀐 브랜치 삭제나 예약·수동 실행은 비인증 자동 갱신에 나타나지 않을 수 있으므로 수동 갱신으로 확인한다.
비인증 한도에 도달하면 카운트다운 대신 일반 화면은 `Rate limit · token needed`, Split view의 각 열은 `GitHub rate limit · token needed`로 표시한다.
두 화면에 같은 재시도 정책을 적용한다.

## 10. 인증 및 GitHub 권한

공개 저장소는 GitHub가 허용하는 범위에서 PAT 없이 조회한다. 비공개 저장소는 사용자가 적용한 Fine-grained PAT로 조회한다.
갱신과 커밋 메타데이터에 관련된 읽기 권한은 다음과 같다.

| 권한                | 용도                    |
| ------------------- | ----------------------- |
| Contents: Read-only | 커밋·브랜치·태그·릴리즈 |
| Actions: Read-only  | Workflow Runs 및 Jobs   |

`Actions: Read-only`는 Actions 조회에만 필요하다. 권한이 부족하면 안내를 표시하되 커밋 그래프는 유지한다.
다른 권한과 토큰 UI는 [공개·비공개 저장소 정책](specification.md#22-공개비공개-저장소)을 따른다.

### 보안 정책

PAT의 저장·복원·삭제와 노출 금지는 위 공통 인증 정책을 따른다.
사용자가 적용한 PAT는 브라우저 localStorage에만 저장하고 GitHub API 요청에만 사용한다.
자체 서버·외부 분석 서비스로 전달하거나 URL·오류 로그에 기록하지 않는다.

## 11. 오류 처리

네트워크 장애·API Rate Limit·토큰 만료·권한 부족·저장소 접근 불가를 구분한다.
일부 브랜치나 태그·릴리즈·Actions 조회가 실패해도 오류를 표시하고 기존 그래프는 유지한다.
일부 페이지만 성공한 결과로 삭제나 데이터 부재를 확정하지 않는다.
오류와 재시도 안내는 [갱신 완료 시각](#24-갱신-완료-시각)과 별도로 관리한다.

저장소·인증 범위가 바뀌면 이전 범위의 요청을 취소하고 늦은 결과를 새 범위에 반영하지 않는다.
Split view의 구성 변경과 공통 한도 대기는 [Split view 갱신·오류 규칙](monitor-mode.md#공통-갱신과-오류)을 따른다.

## 12. 성능

Canvas 2D와 가상 스크롤로 가시 노드를 중심으로 렌더링한다.
DAG 데이터와 메타데이터를 분리하며 [변경된 정보만 반영](#92-변경된-정보만-반영)한다.

미확정 Actions 도넛의 CSS 회전은 화면에 보이는 실행에만 적용한다.
숨긴 탭·화면 밖·완료 상태와 동작 줄이기 설정에서는 회전을 멈춘다.
회전 때문에 DAG 전체를 다시 그리거나 API를 추가 조회하지 않는다.
`angular/angular` 같은 대형 저장소의 탐색 성능은 [공통 검증 기준](specification.md#53-렌더링과-성능)에 따라 확인한다.

## 14. 제외 사항

현재 제품은 다음 기능을 제공하지 않는다.

- GitHub Actions 직접 실행·취소·재실행
- Job별 로그 및 Step 상세 조회
- 실제 Deployment 상태 추적
- 외부 CI 서비스 연동
- 별도 Actions 대시보드
- Actions 전용 갱신 주기 설정
- 브라우저 알림 및 소리
- WebSocket·Webhook 서버
- 서버 측 데이터베이스
- 3D·WebGL 렌더링
- 복잡한 애니메이션

## 15. 유지보수 지침

갱신·메타데이터 동작을 변경할 때는 `RefreshLoop`, API 클라이언트, 데이터 모델의 책임과 캐시 범위를 유지한다.
위 회귀 시나리오에서 변경의 영향을 받는 동작을 확인하고, 코드 변경은 관련 테스트와 빌드로 검증한다.
개발·검증·PR·머지·배포 절차는 [AGENTS.md](../AGENTS.md)를 따르고, 구현 위치는 [문서 안내](README.md)를 참조한다.
